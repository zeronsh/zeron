# Ask: a focused node scrolls into view

**Who needs it:** keyboard and VoiceOver users anywhere in Zeron's app, found in the accessibility pass (Nov 1 2026). Tabbing through a long chat's transcript focuses its tool rows and code-block buttons wherever they are: "Ran 2 commands" took focus at y = −4101, thousands of points above the visible part of its scroll. Nothing scrolled, so the focus ring is off screen and a sighted keyboard user loses their place.

**The problem:** moving focus (Tab, Shift+Tab, `el:focus()`) doesn't bring the focused node into view inside the scroll views that hold it. Browsers do (`focus()` scrolls into view unless `preventScroll`), as do AppKit's key-view loop and GTK.

**The ask:** when focus moves to a node by the keyboard (Tab traversal, a focus group's arrows) or by `focus()`, each scroll view holding it scrolls the least that brings it into view (`nearest`), as `scroll_into_view` does for a list row. Pointer focus (a click) needn't scroll. An opt-out per call (`focus({ scroll = false })`) is fine.

**Today's workaround:** none general. Each screen would have to watch `on_focus` and scroll its own scroll view by hand.

**Adopted (Nov 2, pin `2e22d99d3`).** ds/transcript sets `scroll_padding = { top = 32, bottom = composer + 8 }`; `ui/tests/transcript_focus_scroll.test.luau` tabs both ways through the fixture's long chat. Follow-ups for the zgx lane:
- `scroll_padding` takes a number, not a function or state ("`scroll_padding` is a number or { top, bottom, left, right }"), so it can't follow the composer as it grows; it's read as the list is made, before the composer measures. Zeron passes a one-line composer's height (`foot_rest`): a taller composer covers a focused row by the difference.
- ~~In the transcript, ⇧Tab onto a row above the view left it 137 pt above.~~ **Ours, fixed Nov 2.** zgx's layout lane found the writer with the standalone repro ([`repro-transcript/`](repro-transcript/app.luau), kept as it was): ds/transcript holds its end through a change of size by setting the offset past the end in `ui.after(0, …)`, and `zgx test` drives frames faster than real time, so the launch's timer landed among the keys and clamped the view to its end. (In the app it lands within milliseconds of launch.) ds/transcript now lets the end go when focus has come into the list since the timer was armed; tests/transcript_focus_scroll runs without its old chat switch. zgx offers to make `ui.after(0, …)` mean the next frame exactly, so tests stop racing real time.
- Once the transcript's rows are replaced (a chat switched away and back), ⇧Tab stops at the first row built (four replies up) and wraps round to the composer instead of building the rows above. **Narrowed Nov 2:** the switch only matters because Zeron's chat page reopens the chat at its top (ours, open). The zgx part: ⇧Tab from below a list enters it at its last built row, not its last row, so from a view at the top it walks the built rows and wraps.
