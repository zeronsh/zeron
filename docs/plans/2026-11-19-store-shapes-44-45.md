# Store shapes for amendments 44 and 45

The one copy. The edge and engine lanes drafted these shapes together and
their drafts crossed; the coordinator ruled that this text is the contract
(the edge store lane's final page, plus the coordinator's rulings at the
end). Where a lane's message differs from this file, this file is right.

Times are milliseconds. A record is `{hash, sha256, bytes, key}`.

## Versions

- **States:** `status` is `listed | yanked | taken_down | removed`.
  - `taken_down` is staff's call: harmful, and blocked on devices.
  - `removed` is staff's call: not harmful, not blocked.
- **What the public sees:** `listed` and `yanked` only. The package route
  serves both. A yanked version is never an update offer, only a reinstall.
- **Ordering:** a publish must be later than every existing version, in any
  state. The data file's `newer_rule` says so.
- **An unverified version stops taking new installs when a newer one is
  published.** When a version is listed, every older listed version that is
  not verified becomes `yanked`, with `yanked_by: "superseded"` and the
  version that superseded it (a release supersedes older releases and
  pre-releases; a pre-release supersedes older pre-releases only). Its
  author cannot unyank it. Verified versions are untouched: every verified
  version stays installable, and so does the newest version whether verified
  or not. So no version can sit installable and unread behind a newer one,
  and the queue's one row per plugin loses nothing a person could install.
- **Public `VersionInfo`:** `{version, status, published_at, notes, engines,
  yanked, prerelease, key, hash, sha256, bytes, verified: bool,
  verified_at: ms|null, via: "device"|"deploy_key"}`. `verified` is always
  present, and readers require it.
- **Owner and staff add:** `review: {decided, decision:
  "verified"|"declined"|null, reason?, message?, decided_at?}` and `checks`.
  The public never sees "declined".
- **Every version:** `GET /store/v1/plugins/:id/versions?cursor&limit` →
  `{versions, total, next_cursor?, prev_cursor?}`, listed and yanked, newest
  first.
- **One version:** `GET /store/v1/plugins/:id/versions/:version` → that
  `VersionInfo`, else 404 `not_found` (devices: `not_in_store`).

## Cards and detail

- **`PluginCard` gains** `verified` (its `version` is verified) and
  `verified_version: string|null`. `version` is the newest listed version, a
  release before a pre-release, verified or not.
- **Detail:** `versions` is the first page (5), plus
  `versions_next_cursor?`; `package` is `version`'s record; a device installs
  `verified_version` through the one-version route. There is no
  `verified_package`.
- **The mark is the store's alone.** A version once verified stays verified;
  only a take-down ends it, and a restored version comes back unverified.
  The listing rules refuse a name or summary that claims the mark (the words
  "verified" or "official", a check-mark glyph). A device draws the mark
  only from the record it installs from, fetched at install time: never
  from a card, a remembered offer, the manifest or anything an agent passes.
- **Names too like another's.** Claiming an id one edit, or one confusable
  letter, from an id another account owns with 100 installs or more is
  refused `id_too_similar`; staff can allow it by reservation.
- **Catalog:** `?verified=1` narrows it; `?featured=true` holds only plugins
  whose newest version is verified; featuring a plugin without that is 409
  `not_verified`; `?author=<username>` lists one publisher's plugins: checked against
  the username rule and lowercased before it is a cache key, and an unknown
  username answers the same empty list as one with no plugins.
- **Categories** carry `count`, and `GET /store/v1/stats` answers
  `{plugins, verified}`. Both count exactly the set the lists show (never a
  taken-down, removed or suspended plugin, nor one whose only versions are
  yanked) and are purged with the lists.

## Publish

- `POST /store/v1/plugins/:id/versions` → `201 {id, version, status:
  "listed", verified: false, checks}`, public at once. The same bytes get the
  same answer.

## Updates and take-downs

- **The update check:** `POST /store/v1/updates`, the ask unchanged
  (`verified_only` per plugin is accepted).
- **Each offer:** the newest listed version newer than the installed one that
  fits `engines` and the pre-release choice: `{id, version, hash, sha256,
  bytes, key, publisher, publisher_id, notes, added, removed, prerelease,
  verified, verified_at}`; `verified_update?` has the same shape, present
  only when the offer is unverified and a newer-than-installed verified
  version exists; `in_review` goes; `blocked[]` is unchanged.
- **The take-down feed:** `GET /store/v1/takedowns?after=<seq>` →
  `{events: [{seq, kind: "take_down"|"restore", id, version, reason?}],
  head, reset?}`. Public, cached 60 s per colo, purged on each event.
  - `seq` is a number the store assigns in the same D1 write that takes a
    version down or restores it, in commit order. A device never sends a
    time; `after` is the last `seq` it applied. A cached answer can only
    delay an event, never skip one. Pages hold at most 500, in `seq` order.
  - The feed keeps 30 days. An `after` older than that, or none, answers
    `{reset: true, head}`: the device runs the full update check (which
    reports blocks on what it has installed, and clears blocks the store no
    longer names) and then continues from `head`.
  - Devices poll every 15 minutes and match events against their installs
    locally, sending nothing about them. The full check stays at 6 hours.
  - A take-down guards the honest case. A plugin that runs programs can
    undo its own block on a device; what stands against a hostile plugin is
    the consent sheet saying that it runs programs.

## Deploy keys (44)

- **List:** `GET /store/v1/me/keys` → `{keys: [{key, name, scope,
  created_at, last_used_at, last_used_plugin, expires_at, revoked_at?}]}`.
  `scope` is `{all: true}` or `{plugins: [ids, sorted, unique]}`.
- **Create:** `POST /store/v1/me/keys {key, name, scope, expires?, proof,
  stepUp}` → 201. Session only, with a step-up `for: "deploy_key"`, used
  once. 1–50 ids, each owned now. Refusals: 400 `{error: "invalid_scope",
  ids?}`; 403 `{error: "not_owner", ids}`.
- **Revoke:** `DELETE /store/v1/me/keys/:key` → `{revoked: true}`.
- **Proof v2:** the key signs `"zeron-deploy-key:v2:" + publisher_id + ":" +
  expiry + ":" + scopeText + ":" + key`, where `publisher_id` is the
  account's opaque publisher id (amendment 33), `expiry` is the key's
  `expires_at` in ms or `never`, and `scopeText` is `*` for all, else the
  ids, each checked against the id rule, sorted by code unit (JavaScript's
  default sort and Rust's string order agree for these), a duplicate refused
  rather than dropped, joined with `,`.
  A proof is good for one account's key with one lifetime and one scope. v1
  is refused. The engine generates the data file (`proof_prefix` v2)
  and the vectors (cases for `*` and for two sorted ids); the edge takes both
  unedited.
- **A signed request may:** `POST /plugins/:id/versions` when the id exists,
  the key's account owns it now, and it is in scope; never a new id (403
  `key_not_allowed`); `GET /me/plugins` (the in-scope plugins it owns);
  nothing else.
- **`/plugin-keys/:key?plugin=`:** verified only when the key is live, the
  plugin is in scope, and the account owns it.
- **Leaving and arriving:** ownership is checked at each use. A plugin that
  leaves the account is removed from every key's scope for good; coming
  back does not restore it. `all` means the plugins the account owned when
  the key was made and those it first publishes later, never a plugin
  transferred in.
- **Limits:** at most 20 live keys an account, and 10 keys made a day.
- **A publish through a key** raises a notice on the author's own devices
  (which key published which version).

## Author and staff

- **Author:** `withdraw` goes; `yank` and `unyank` stay. In `/me/plugins`,
  versions carry `review`, and `listing` is `listed | unlisted | suspended`.
- **Staff queue:** `GET /admin/queue?state=undecided|verified|declined|all`,
  default undecided, oldest first, versions with open reports first. One row
  per plugin: its newest undecided version, saying how many earlier
  undecided versions it superseded (those are yanked by the rule above, and
  a reviewer can still open each from the plugin's staff page). Items as amendment 40, plus
  `status`, `review`, `reports`. `base` is the newest verified other version.
- **Staff actions:** `GET /admin/versions/:id/:version`; `POST …/verify`
  (from undecided or declined); `POST …/decline {reason, message}` (from
  undecided); `POST /admin/plugins/:id/versions/:version/take-down {reason}`
  (blocks); `POST …/remove {reason}` (does not block). Each needs the version
  listed or yanked, else 409 `invalid_state`.
- **Audit:** `version.publish` (the author is the actor; `detail {via,
  key}`), `verify`, `decline`, `take_down`, `remove`, `yank`, `unyank`, and
  `plugin.*`, `report.*`, `reservation.*` as now.

## Coordinator's rulings

- **Sorts are honest.** Every sort is exactly its own key, verified or not;
  `verified=1` is a filter; search relevance uses `verified` only to break
  ties. Featured is the vetted shelf.
- **The device's update preference** (`store_updates: "newest" |
  "verified"`, device-wide, with a per-plugin override) defaults to
  `newest`: the newest version is offered and staged, marked when not
  verified, with the newest verified one beside it. One constant.
- **Consent:** installing or updating to an unverified store version always
  asks, even when it asks for nothing new.
- **Agents install only verified versions.** A store install by an agent
  takes `verified_version`, or a named version that is verified; anything
  else is refused `needs_person`, whether or not a verified version exists
  (a new plugin nobody has read, a squat, a plugin whose verified versions
  were yanked). An agent never updates an installed store plugin.
- **Updates in bulk never take unverified code.** Any "update all" applies
  verified updates only; an unverified update is always its own action,
  with its own question, and its sheet says when the installed version was
  verified and this one is not.
- **Every publish not made on this device raises a notice** on the author's
  devices: which version, and whether another device or which key sent it.
- **No cap tied to review speed:** the hourly, daily and new-id limits stay
  as they are.
- **Reports** reorder the queue and never hide a plugin by themselves.

## Names settled while building

- **Restore:** `POST /store/v1/admin/plugins/:id/versions/:version/restore
  {reason}` takes a `taken_down` version back to `listed`, unverified,
  writes a `restore` event and `version.restore` in the audit, and lifts the
  block.
- **The queue row** carries `earlier_undecided: n`.
- **For staff,** `GET /admin/versions/:id/:version` carries `superseded:
  {at, by} | null`, and the plugin's staff page lists each version with it.
- **The publish notice:** the owner's view of a version in `/me/plugins`
  carries `via`, `key` (the signer) and `deploy_key: {key, name} | null`. A
  device tells "another device" by `via: "device"` with a key that is not its
  own, and "which key" by `deploy_key.name`.
- **`id_too_similar`** is measured on the username rules' `skeleton`: a new
  id is refused when its skeleton equals, or is one edit from, the skeleton
  of an id another account owns with 100 installs or more. At claim only.
- **What `all` covers:** a plugin has `owner_since`; it is in an `all` key's
  scope when it was owned when the key was made, or the account claimed it
  and it has never changed hands.
- **Email:** the edge sends none today. The device notice stands alone until
  a provider and a sending domain are decided.
