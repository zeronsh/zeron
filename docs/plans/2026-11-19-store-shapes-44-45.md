# Plugin store: the shapes for amendments 44 and 45

The one copy of what the edge serves and the engine reads for amendments 44
(a deploy key belongs to an account and carries a scope) and 45 (publishing
is immediate; review verifies). Agreed by the edge store lane and the engine
lane, accepted by the coordinator with the rulings below. Where a lane's
message and this file differ, this file is right; a change is made here.

Times are epoch ms. A record is `{url, bytes, sha256, hash, key}`: what a
device installs a version by.

## Versions

- `status`: `listed | yanked | taken_down | removed`.
  - `taken_down`: staff, harmful: blocked on devices (`blocked[]`, the
    take-down feed).
  - `removed`: staff, not harmful: gone, not blocked.
  - Public routes show `listed` and `yanked` only. A yanked version is never
    an update offer, only a reinstall.
- A publish must be later than every existing version of the plugin, in any
  state (the data file's `newer_rule`).
- Public `VersionInfo`: `{version, status, published_at, notes, engines,
  yanked, prerelease, key, hash, sha256, bytes, verified, verified_at, via}`.
  `verified` is always present and required to read a version; `via` is
  `device | deploy_key`.
- Owner and staff only: `review: {decided, decision: "verified" | "declined"
  | null, reason?, message?, decided_at?}`, and `checks`. The public never
  sees `declined`, only `verified: false`.
- `GET /store/v1/plugins/:id/versions?cursor&limit` → `{versions, total,
  next_cursor?, prev_cursor?}`: listed and yanked, newest first.
- `GET /store/v1/plugins/:id/versions/:version` → that `VersionInfo`, else
  404 `not_found` (a device says `not_in_store`). Devices install a named
  version, `verified_version` included, through it.
- `…/versions/:version/package` serves any listed or yanked version.

## Cards, the detail, the catalog

- `PluginCard` += `verified` (its `version` is verified) and
  `verified_version` (the newest verified listed version, or null).
  `version` is the newest listed version (release before pre-release),
  verified or not.
- Detail: `package` is `version`'s record; `versions` is the first page (5)
  plus `versions_next_cursor?`.
- Catalog: `?verified=1` narrows to `verified: true`; `?author=<username>`
  lists a publisher's plugins (case-insensitive; an unknown one is
  `{items: [], total: 0}`); `featured=true` also needs a `verified_version`
  (featuring a plugin without one is 409 `not_verified`).
- `GET /store/v1/categories` → `{categories: [{id, name, count}]}`, `count`
  the listed plugins in it.
- `GET /store/v1/stats` → `{plugins, verified}` (listed plugins; those whose
  newest version is verified). Cached.

## Publish and your plugins

- `201 {id, version, status: "listed", verified: false, checks}`: public at
  once.
- Author actions: `yank`, `unyank`. `withdraw` goes; `remove` is staff only.
- `GET /store/v1/me/plugins`: each version carries `verified`,
  `verified_at`, `via` and `review` (above).
- A version published through a deploy key is said on the author's own
  devices (see Notices).

## Updates

- `POST /store/v1/updates`: the ask is unchanged.
- Each `updates[]` offer: the newest listed version newer than the one
  installed that fits `engines` and the pre-release choice: `{id, version,
  hash, sha256, bytes, key, publisher, publisher_id, notes, added, removed,
  prerelease, verified, verified_at}`, `verified` always present.
- `verified_update?`: the same shape, present only when the offer is
  unverified and a verified version newer than the one installed exists.
- `in_review` goes. `blocked[]` unchanged.

## Take-downs

- `GET /store/v1/takedowns?since=<ms>` → `{takedowns: [{id, version,
  reason, at}], now, next_since?}`: public, the same for everyone, cached
  60 s per colo and purged at each take-down; `since` exclusive, oldest
  first, at most 500 a page.
- Devices poll it every 15 minutes with the last `now` (or `next_since`)
  and match what's installed. The full update check stays at 6 hours. A
  take-down reaches a device in at most 15 minutes and 60 s of cache.

## Notices

## Deploy keys (44)

- `GET /store/v1/me/keys` → `{keys: [{key, name, scope, created_at,
  last_used_at, last_used_plugin, expires_at, revoked_at?}]}`.
- `POST /store/v1/me/keys {key, name, scope, expires?, proof, stepUp}` →
  `201` that key. Session only; a step-up begun `for: "deploy_key"`, used
  once.
  - `scope`: `{all: true}` or `{plugins: [id…]}`: 1–50 ids, sorted, unique,
    each the caller's now.
  - 400 `{error: "invalid_scope", ids?}`; 403 `{error: "not_owner", ids}`.
- `DELETE /store/v1/me/keys/:key` → `{revoked: true}`.
- Proof v2 signs `"zeron-deploy-key:v2:" + scopeText + ":" + key`;
  `scopeText` is `*` for all, else the sorted ids joined with `,`. v1 is
  refused. The data file's `deploy_key.proof_prefix` is
  `zeron-deploy-key:v2:`; the vectors hold both forms.
- A signed request may: `POST /store/v1/plugins/:id/versions` when the
  plugin exists, the key's account owns it now and it is in scope (never a
  new id: 403 `key_not_allowed`); `GET /store/v1/me/plugins` (its in-scope
  plugins). Nothing else.
- `GET /plugin-keys/:key?plugin=<id>`: verified only when the key is live,
  `<id>` is in its scope and its account owns it.
- A transfer no longer revokes keys: ownership is checked at each use.

## Staff (the edge's)

- `GET /admin/queue?state=undecided|verified|declined|all` (default
  `undecided`): one row per plugin, its newest undecided version, oldest
  first, reported ones first. Nothing on a device depends on an older
  undecided version being reviewed.
- `POST /admin/versions/:id/:version/verify` (from undecided or declined),
  `…/decline {reason, message}`;
  `POST /admin/plugins/:id/versions/:version/take-down {reason}`,
  `…/remove {reason}`. A version in the wrong state: 409 `invalid_state`.
- Audit: `version.publish` (`detail {via, key}`), `version.verify`,
  `version.decline`, `version.take_down`, `version.remove`,
  `version.yank`, `version.unyank`.

## The device (engine)

- Consent: installing or updating to an unverified version always asks,
  even when it asks for nothing new; a verified one keeps today's rule. The
  plugins list marks a running unverified version.
- Update preference, device-wide and per plugin: `newest` (the default, one
  constant) or `verified`. With `newest`, the newest version is offered and
  staged, marked not verified when it isn't, the newest verified offered
  beside it (`verified_update`); with `verified`, the verified one is staged.
- Agents: an agent's store install without a `version` takes
  `verified_version` when there is one, else the newest, landing waiting.
  An agent naming an unverified version is refused (`needs_person`) when a
  verified version exists; when none does it lands waiting, marked "not
  verified, chosen by an agent". Agents never update (`needs_person`).
- The author-only path to a version in review (`own_record`, `in_review`)
  goes: no version is installable by one account and not another.
- The CLI's publish says the version is live now and not yet verified, and
  prints the plugin's store address.
