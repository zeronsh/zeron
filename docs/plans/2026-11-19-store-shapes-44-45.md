# Store shapes for amendments 44 and 45

The one copy. The edge and engine lanes drafted these shapes together and
their drafts crossed; the coordinator ruled that this text is the contract
(the edge store lane's final page, plus the coordinator's rulings at the
end). Where a lane's message differs from this file, this file is right.

Times are milliseconds. A record is `{hash, sha256, bytes, key}`.

## Versions

- **States:** `status` is `listed | yanked | taken_down | removed`.
  - `taken_down` is staff's call: harmful, and blocked on devices.
  - `removed` is staff's call: not harmful, not blocked.
- **What the public sees:** `listed` and `yanked` only. The package route
  serves both. A yanked version is never an update offer, only a reinstall.
- **Ordering:** a publish must be later than every existing version, in any
  state. The data file's `newer_rule` says so.
- **An unverified version stops taking new installs when a newer one is
  published.** When a version is listed, every older listed version that is
  not verified becomes `yanked`, with `yanked_by: "superseded"` and the
  version that superseded it (a release supersedes older releases and
  pre-releases; a pre-release supersedes older pre-releases only). Its
  author cannot unyank it. Verified versions are untouched: every verified
  version stays installable, and so does the newest version whether verified
  or not. So no version can sit installable and unread behind a newer one.
  A superseded yank is for good: a take-down, a remove or an author's yank
  of a newer version brings nothing back, and the author publishes again.
  If that leaves a plugin with nothing installable, it leaves the lists.
  - **Verifying a superseded version clears its superseded yank** (every
    verified version is installable); an author's own yank stays.
  - **A restore applies the rule again:** a restored version comes back
    unverified, and straight to `yanked_by: "superseded"` when anything
    newer on its line is listed.
  - **One write:** the "later than every version" check, the insert and the
    superseding are one D1 batch, after the package is stored, so a publish
    that fails supersedes nothing. A retried publish of the same bytes
    answers that version's current state and changes nothing.
  - Superseding does not look at `engines`: an unverified version that
    needs a newer Zeron can leave older Zerons with nothing to install until
    it or an earlier one is verified. That is the author's to weigh.
- **Public `VersionInfo`:** `{version, status, published_at, notes, engines,
  yanked, prerelease, key, hash, sha256, bytes, verified: bool,
  verified_at: ms|null, via: "device"|"deploy_key"}`. `verified` is always
  present, and readers require it.
- **Owner and staff add:** `review: {decided, decision:
  "verified"|"declined"|null, reason?, message?, decided_at?}` and `checks`.
  The public never sees "declined".
- **Every version:** `GET /store/v1/plugins/:id/versions?cursor&limit` →
  `{versions, total, next_cursor?, prev_cursor?}`, listed and yanked, newest
  first.
- **One version:** `GET /store/v1/plugins/:id/versions/:version` → that
  `VersionInfo`, else 404 `not_found` (devices: `not_in_store`).

## Cards and detail

- **`PluginCard` gains** `verified` (its `version` is verified) and
  `verified_version: string|null`. `version` is the newest listed version, a
  release before a pre-release, verified or not.
- **`PluginCard.cover: string | null`** (Nov 24): the first screenshot of the
  card's `version`, as a path in that version's package (amendment 35:
  pictures are package paths, never URLs, as `icon` and `screenshots` are),
  fetched through `GET /store/v1/plugins/:id/files/:version/:path` with the
  card's `version`. Null when that version has no screenshots (never another
  version's) and when nothing is listed. A version taken down moves the card,
  and its cover, to the version it then shows. Edge: `plugins.cover`, kept by
  `relist`, migration `0002_card_cover.sql`.
- **Detail:** `versions` is the first page (5), plus
  `versions_next_cursor?`; `package` is `version`'s record; a device installs
  `verified_version` through the one-version route. There is no
  `verified_package`.
- **The mark is the store's alone.** A version once verified stays verified;
  only a take-down ends it, and a restored version comes back unverified.
  The listing rules refuse a name or summary that claims the mark (the words
  "verified" or "official", a check-mark glyph). Where a person decides or is told what
  they are running (the consent sheet, the update sheet, an installed
  plugin's row), a device draws the mark only from the record it installs
  from, fetched at install time: never from a card, a remembered offer, the
  manifest or anything an agent passes. Where it only shows the catalog
  (Browse's rows, a plugin's store page), it shows what the store's answer
  says, fetched for that visit and not kept past it.
- **Names too like another's.** Claiming an id one edit, or one confusable
  letter, from an id another account owns with 100 installs or more is
  refused `id_too_similar`; staff can allow it by reservation.
- **Catalog:** `?verified=1` narrows it; `?featured=true` holds only plugins
  whose newest version is verified; featuring a plugin without that is 409
  `not_verified`; `?author=<username>` lists one publisher's plugins: checked against
  the username rule and lowercased before it is a cache key, and an unknown
  username answers the same empty list as one with no plugins.
- **Categories** carry `count`, and `GET /store/v1/stats` answers
  `{plugins, verified}`. Both count exactly the set the lists show (never a
  taken-down, removed or suspended plugin, nor one whose only versions are
  yanked) and are purged with the lists.

## Publish

- `POST /store/v1/plugins/:id/versions` → `201 {id, version, status:
  "listed", verified: false, checks}`, public at once. The same bytes get the
  same answer.

## Updates and take-downs

- **The update check:** `POST /store/v1/updates`, the ask unchanged
  (`verified_only` per plugin is accepted).
- **Each offer:** the newest listed version newer than the installed one that
  fits `engines` and the pre-release choice: `{id, version, hash, sha256,
  bytes, key, publisher, publisher_id, notes, added, removed, prerelease,
  verified, verified_at}`; `verified_update?` has the same shape, present
  only when the offer is unverified and a newer-than-installed verified
  version exists; `in_review` goes; `blocked[]` is unchanged.
- **The take-down feed:** `GET /store/v1/takedowns?after=<seq>` →
  `{events: [{seq, kind: "take_down"|"restore", id, version, reason?}],
  head, reset?}`. Public, cached 60 s per colo, purged on each event.
  - `seq` is a number the store assigns in the same D1 write that takes a
    version down or restores it, in commit order. A device never sends a
    time; `after` is the last `seq` it applied. A cached answer can only
    delay an event, never skip one. Pages hold at most 500, in `seq` order.
  - The feed keeps 30 days. An `after` older than that, or none, answers
    `{reset: true, head}`: the device runs the full update check (which
    reports blocks on what it has installed, and clears blocks the store no
    longer names) and then continues from `head`.
  - Devices poll every 15 minutes and match events against their installs
    locally, sending nothing about them. The full check stays at 6 hours.
  - A take-down guards the honest case. A plugin that runs programs can
    undo its own block on a device; what stands against a hostile plugin is
    the consent sheet saying that it runs programs.

## Deploy keys (44)

- **List:** `GET /store/v1/me/keys` → `{keys: [{key, name, scope,
  created_at, last_used_at, last_used_plugin, expires_at, revoked_at?}]}`.
  `scope` is `{all: true}` or `{plugins: [ids, sorted, unique]}`.
- **Create:** `POST /store/v1/me/keys {key, name, scope, expires?, proof,
  stepUp}` → 201. Session only, with a step-up `for: "deploy_key"`, used
  once. 1–50 ids, each owned now. Refusals: 400 `{error: "invalid_scope",
  ids?}`; 403 `{error: "not_owner", ids}`.
- **Revoke:** `DELETE /store/v1/me/keys/:key` → `{revoked: true}`.
- **Proof v2:** the key signs `"zeron-deploy-key:v2:" + publisher_id + ":" +
  expiry + ":" + scopeText + ":" + key`, where `publisher_id` is the
  account's opaque publisher id (amendment 33), `expiry` is the key's
  `expires_at` in ms or `never`, and `scopeText` is `*` for all, else the
  ids, each checked against the id rule, sorted by code unit (JavaScript's
  default sort and Rust's string order agree for these), a duplicate refused
  rather than dropped, joined with `,`.
  A proof is good for one account's key with one lifetime and one scope. v1
  is refused. The engine generates the data file (`proof_prefix` v2)
  and the vectors (cases for `*` and for two sorted ids); the edge takes both
  unedited.
- **A signed request may:** `POST /plugins/:id/versions` when the id exists,
  the key's account owns it now, and it is in scope; never a new id (403
  `key_not_allowed`); `GET /me/plugins` (the in-scope plugins it owns);
  nothing else.
- **`/plugin-keys/:key?plugin=`:** verified only when the key is live, the
  plugin is in scope, and the account owns it.
- **Leaving and arriving:** ownership is checked at each use. A plugin that
  leaves the account is removed from every key's scope for good; coming
  back does not restore it. `all` means the plugins the account owned when
  the key was made and those it first publishes later, never a plugin
  transferred in.
- **Limits:** at most 20 live keys an account, and 10 keys made a day.
- **A publish through a key** raises a notice on the author's own devices
  (which key published which version).

## Author and staff

- **Author:** `withdraw` goes; `yank` and `unyank` stay. In `/me/plugins`,
  versions carry `review`, and `listing` is `listed | unlisted | suspended`.
- **Staff queue:** `GET /admin/queue?state=undecided|verified|declined|all`,
  default undecided, oldest first, versions with open reports first. The
  queue holds every undecided version the superseding rule has not yanked:
  at most two rows a plugin, its newest undecided release and its newest
  undecided pre-release when that is newer. A version leaves the queue only
  by a decision or by the rule that yanks it, so nothing that leaves it
  unread can be installed. Each row says how many earlier undecided versions
  it superseded (a reviewer can still open each from the plugin's staff
  page). Items as amendment 40, plus
  `status`, `review`, `reports`. `base` is the newest verified other version.
- **Staff actions:** `GET /admin/versions/:id/:version`; `POST …/verify`
  (from undecided or declined); `POST …/decline {reason, message}` (from
  undecided); `POST /admin/plugins/:id/versions/:version/take-down {reason}`
  (blocks); `POST …/remove {reason}` (does not block). Each needs the version
  listed or yanked, else 409 `invalid_state`.
- **Audit:** `version.publish` (the author is the actor; `detail {via,
  key}`), `verify`, `decline`, `take_down`, `remove`, `yank`, `unyank`, and
  `plugin.*`, `report.*`, `reservation.*` as now.

## Coordinator's rulings

- **Sorts are honest.** Every sort is exactly its own key, verified or not;
  `verified=1` is a filter; search relevance uses `verified` only to break
  ties. Featured is the vetted shelf.
- **The device's update preference** (`store_updates: "newest" |
  "verified"`, device-wide, with a per-plugin override) defaults to
  `newest`: the newest version is offered and staged, marked when not
  verified, with the newest verified one beside it. One constant.
- **Consent:** installing or updating to an unverified store version always
  asks, even when it asks for nothing new.
- **Agents install only verified versions.** A store install by an agent
  takes `verified_version`, or a named version that is verified; anything
  else is refused `needs_person`, whether or not a verified version exists
  (a new plugin nobody has read, a squat, a plugin whose verified versions
  were yanked). An agent never updates an installed store plugin.
- **Updates in bulk never take unverified code.** Any "update all" applies
  verified updates only; an unverified update is always its own action,
  with its own question, and its sheet says when the installed version was
  verified and this one is not.
- **Every publish not made on this device raises a notice** on the author's
  devices: which version, and whether another device or which key sent it.
  The engine keeps it until the app is there to show it, once per version.
- **No cap tied to review speed:** the hourly, daily and new-id limits stay
  as they are.
- **Reports** reorder the queue and never hide a plugin by themselves.

## Names settled while building

- **Restore:** `POST /store/v1/admin/plugins/:id/versions/:version/restore
  {reason}` takes a `taken_down` version back to `listed`, unverified,
  writes a `restore` event and `version.restore` in the audit, and lifts the
  block.
- **The queue row** carries `earlier_undecided: n`.
- **For staff,** `GET /admin/versions/:id/:version` carries `superseded:
  {at, by} | null`, and the plugin's staff page lists each version with it.
- **The publish notice:** the owner's view of a version in `/me/plugins`
  carries `via`, `key` (the signer) and `deploy_key: {key, name} | null`. A
  device tells "another device" by `via: "device"` with a key that is not its
  own, and "which key" by `deploy_key.name`.
- **`id_too_similar`** is measured on the username rules' `skeleton`: a new
  id is refused when its skeleton equals, or is one edit from, the skeleton
  of an id another account owns with 100 installs or more. At claim only.
- **What `all` covers:** a plugin has `owner_since`; it is in an `all` key's
  scope when it was owned when the key was made, or the account claimed it
  and it has never changed hands.
- **Email:** the edge sends none today. The device notice stands alone until
  a provider and a sending domain are decided.
- **From the edge's build (b467e6299):** the publish answer adds
  `superseded: [versions]`; an owner's versions carry `yanked_by:
  "author"|"superseded"` and `superseded {at, by}`; a transfer sets
  `owner_since` strictly later than the claim and than any earlier transfer;
  registering a revoked key again is 409 `key_revoked`, the same key under
  another scope 409 `key_taken`; `/plugin-keys` shows `scope` to the key's
  owner only; the audit has `version.restore`; the staff view of a version
  carries `decisions {verified, declined}`.
- **The schema is one file,** `edge/migrations/store/0001_store.sql`. No
  database existed before it; a database made by hand from the older files
  is recreated, not migrated.
- **`GET /store/v1/me/plugins` answers `{publisher_id, plugins}`,** to a
  session and to a key alike, with plugins or none: a device needs its own
  publisher id for proof v2 before it has a plugin.
- **The mark-claiming rule** (engine 1128fe31c, edge bc60237ba): `bad_listing`
  on a name or description that, folded (NFKC, lowercase, NFKD with
  nonspacing marks dropped), holds a check-mark glyph or the whole word
  "verified" or "official". The edge alone also maps look-alike letters of
  other alphabets first; the vectors hold the edge to `edge_problems` and
  the device's check to `problems`.
- **A cached answer's key is built from the value its handler uses, read
  once.** A take-down feed `after` that is not `^[0-9]{1,15}$` is 400 and
  never cached; a search with no searchable word is keyed as a search.
- **The public `VersionInfo` says why a version takes no new installs:**
  `yanked_by: "author"|"superseded"|null` and, when superseded,
  `superseded_by: <version>`. A plugin's page can then say "Replaced by
  1.3.0 before it was verified" without the owner's view.
- **Look-alikes come from the standard, in one table.** The engine
  generates, from Unicode's confusables.txt (UTS #39), the look-alikes of the
  letters "verified" and "official" use, plus the digit folds, into the data
  file with the Unicode version and the source's hash. The device's check
  and the edge both read it: one rule, one answer (`edge_problems` goes).
  The glyph list gains √ and U+10102.
- **A name or summary cannot say the plugin is Zeron's own unless it is.**
  After the same folding, "by zeron", "from zeron", "zeron team", "zeron's
  own", and "zeron" directly followed by approved, certified, endorsed,
  recommended or staff are refused `claims_zeron`, unless the publisher
  carries Zeron's own badge. The edge enforces it; the device warns.
  "Zeron's own badge" is the publisher's `maintainer` badge: only staff grant
  it, at the edge, and nothing a publisher sends can set it. A device cannot
  know the publisher, so its shared check gives a warning; a publish is
  refused 400 `claims_zeron` with its sentence.
- **What the engine tells a sheet about an unverified store version.** An
  update's item carries `update.verified` (bool), `update.installed_verified`
  (bool) and `update.verified_alternative`; a first install's item carries
  `source.verified` and `source.verified_alternative`, the same name and
  shape in both places: `{version, added, removed, notes?, verified_at?} |
  null` (as the engine built it at acc084360; `added` and `removed` are
  what it asks for against the version being asked about). The alternative is the newest verified version this Zeron can run
  that is not the one being asked about (for an update, newer than the
  installed one), or null. `nothing_new: true` marks an item that asks
  again only because the version is not verified. A sheet's "instead"
  action is the host's (`plugins.install_verified {id, hash}`), which asks
  the engine `InstallVerifiedPlugin {id, hash}` (b1bd30e10): the engine
  reads the version from its own pending item, never from the host or a
  script, fetches that version's record then, and refuses `not_verified`
  unless that record says verified.
- **One sheet for an unverified update.** Installed's Update link stages the
  update and the consent window opens with the warning, the line on the
  installed version ("The version you have, 1.2.0, was verified." when it
  was) and the "instead" action; the store page's update sheet says the
  same. Never two questions for one update.
- **A notice is only for the account's own publishes.** The owner's view of
  each version in `/me/plugins` also carries `publisher_id`: the account
  that published that version, fixed at publish and unchanged by a transfer
  (the id offers already carry in public). A device raises a publish notice
  only for versions whose `publisher_id` is the account's own, the
  top-level `publisher_id` of `/me/plugins`; a version with no
  `publisher_id` is noticed (the safe side). So a plugin transferred in
  brings no notices for its former owner's versions.
- **The link can name a version.** `zeron://open/plugin/<id>?version=<v>`
  opens that plugin's page with that version chosen: its Install acts on
  `<v>`, says so on the button ("Install 1.2.0"), and the page shows that
  version's state. `<v>` must read as a version (the same cleaning as
  anywhere a version is said) or the link opens the page as if it had none;
  any other query key is ignored. Nothing else changes: the page arms its
  buttons after `ARM_MS`, the install asks as any install does, and the
  device takes the mark from that version's record. The web uses it for
  "Install 1.2.0" beside an unverified newest version, and on a version's
  own page.
- **Who does what, in words.** Zeron verifies ("Zeron hasn't verified 1.3.0
  yet", "Verified"); a reviewer reads ("Waiting for a reviewer", "until a
  reviewer has read it", "The reviewer's note"). The three states are
  "verified", "not verified yet" (no decision) and "not verified"
  (declined, to its author only). The app and the web use the same words.

## Claims of being Zeron's, after the identity lane's attack

- **"zeron" is read as the mark words are:** the same folding, look-alike
  table, spacing join and unseen-character removal, before any test below.
- **In a plugin's name, "zeron" is refused unless it is said about Zeron,
  not as Zeron.** Allowed only as the object of a short list of forms kept
  in the data file for the store's own locales (English: "for Zeron", "in
  Zeron", "with Zeron", "on Zeron", "to Zeron"; the Chinese forms beside
  them). Any other use in a name ("Zeron Labs", "Team Zeron", "Zeron Git",
  "Zeron's git", "Zeron-made") is `claims_zeron`, unless the publisher
  carries `maintainer`. A name that leads with the brand reads as ours.
- **In a summary or description, the phrase test stays, wider.** Refused:
  "zeron" directly after a word of origin (by, from, "by the", made by,
  built by; von, par, de, da, di, del, van) or directly before or after a
  word of standing (team, labs, inc, hq, staff, approved, certified,
  endorsed, recommended, made, built; 官方, 公式, 공식). Prose about Zeron
  ("adds a panel to Zeron's sidebar") passes. The lists are in the data
  file; the edge and the device read them.
- **The mark words in other languages.** "verified" and "official" are
  also refused in Spanish, French, German, Italian, Portuguese, Russian,
  Chinese, Japanese and Korean (a short list in the data file), whole words
  for scripts with spaces and as substrings for Chinese, Japanese and
  Korean. This also refuses "no oficial" and "非官方", as "not official" is
  refused in English: the author rewords.
- **A claim does not outlive the badge.** A transfer of a plugin whose name
  or summary would be `claims_zeron` for the new owner is refused (409
  `claims_zeron`) until it is renamed. Revoking `maintainer` from an account
  sets `listing: suspended` on each of its plugins that would now be
  refused, names them in the answer and in the audit, and their installed
  copies keep running.
- **Usernames.** The reserved check reads a username with the digit folds
  (0 for o, 3 for e, 2 for z, 1 for i or l) and with runs of one letter
  collapsed, so "zer0n", "2eron", "zerron" and "zeeron" are refused as
  "zeron" is. A username one different letter away ("xeron", "heron") is
  not refused: the badge, not the handle, is what says a plugin is ours.

## What the site's pages ask of the catalog

- **`GET /store/v1/stats`** also answers `new_7d`: plugins first listed in
  the last seven days, counted over the same set the lists show.
- **`GET /store/v1/categories?top=<n>`** (n ≤ 4) adds `top` to each
  category: its n most installed plugins as `PluginCard`s, the same order
  and set `?category=<id>&sort=popular` gives. Without `top`, as now.
- **`GET /store/v1/keywords?category=<id>&limit=<n>`** (n ≤ 24; `category`
  optional) → `{keywords: [{keyword, count}]}`, the most used keywords among
  the plugins the lists show, most used first, ties by keyword. `count` is
  the number of listed plugins carrying it.
- **`sort=verified`** on the catalog: plugins that have a verified version,
  by when their newest verified version was verified, newest first (ties by
  the stable key, as every sort). A `PluginCard` carries `verified_at`: that
  time, or null when it has no verified version. This is the site's "Newly
  verified" shelf; it is its own honest sort, not a re-ranking of another.
- All of these are public, cached as the catalog is, and keyed on their
  whole query.
- A category's one-line description is the site's own words (not the
  edge's). The device a version was published from is not named anywhere:
  the site says "one of your devices", as the app's notice does.
- **Keywords are held to both rules.** A keyword is read as a name is (the
  same folding, digit folds and `i`/`l`), with "-" as a separator between
  its parts. It is refused when a part, or its parts joined, is a mark word
  (in any of the listed languages that can be written in a keyword's
  letters), and it is refused when any part is "zeron": every plugin here
  is for Zeron, so the word says nothing in a keyword and only ever serves
  a claim. No badge lifts this. Keywords show on cards and in the store's
  own keyword list, so they are part of what the store says.
- **The other-language mark words must not refuse ordinary words.** A word
  goes in the bare list only when its matched form has no common other
  meaning in text about software. Where it has one, the rule narrows:
  - French "vérifié" folds to "verifie", which is also "vérifie" (checks).
    In a name the folded form is refused; in a summary or description only
    the accented participle ("vérifié", "vérifiée", and plurals) is.
  - 公式 is "official" in Japanese and "formula" in Chinese: refused bare
    only in a text that also holds kana.
  - 공식 (official, formula), 认证 / 認證 / 認証 / 인증 (certified,
    authentication) are not refused bare. Unambiguous forms are: 官方,
    已验证 / 已驗證, 已认证 / 已認證, 認証済み, 検証済み, 確認済み, 인증됨,
    검증됨, 확인됨 (the engine lane may correct this list with reasons).
  - Beside "zeron", every one of them is still refused by the claims rule,
    and so are the Chinese words of origin 由 and 来自 in a summary or
    description.
  The vectors carry honest cases that must pass: "Vérifie la syntaxe de vos
  fichiers", "数学公式编辑器", "수학 공식", "身份认证", "認証トークン", "인증
  토큰".
- **Which window asks.** The consent window is the one place a person
  allows an unverified version. From Installed, Update on an unverified
  offer stages it and the consent window opens (0881e0bb3): not the store
  page, not a second sheet. On a store page, the update sheet stays what it
  was, "what's new, and what changes": for an unverified offer its warning
  states the fact, offers the verified alternative, and says that Zeron
  asks before it installs (as its new-publisher callout already says);
  pressing Update there leads to the consent window, which asks. One click
  still never takes unverified code: the update is staged, waiting.
- **An installed version can become verified.** At each update check the
  device also re-reads the record of the version it runs; when that record
  now says verified and names the same package (hash), the install record's
  `verified` becomes true with its `verified_at`. Never the reverse from a
  check (a verified version stays verified; take-downs come by the feed).
  So a row that said "not verified yet" stops saying it once Zeron has
  read that version.
- **Saying a plugin is part of Zeron is a claim too.** Words of belonging:
  built-in (builtin, built in, built into), bundled, included, preinstalled
  (pre-installed), ships (shipped), comes with, native, default, stock,
  core, first-party, part of. In a **name** that holds "zeron", any of them
  anywhere is `claims_zeron` ("Built-in Zeron Git", "Default Git for
  Zeron"). In a **summary or description**, one of them directly before

- **Japanese and Korean "official", narrowed further:** 公式 and 公認 only

## The mark's words in a summary: only when said of the plugin itself

The identity lane measured the rule above on 79 honest plugin-style texts in
ten languages: 25 were refused as descriptions, 17 of them for naming
someone else's verified or official thing ("Opens the official Rust
documentation", "Shows GitHub's verified badge") and 6 for "unofficial" in
languages where it is two words. A rule that refuses honest text that often
is wrong. This section replaces the bare-word refusal **in a summary or
description**. Names and keywords stay as they are: there any mark word is
refused (with the ambiguity narrowing above), because a rename is cheap and
the name sits beside the seal.

- **In a summary or description, a mark word (any listed language, read
  with the same fold, digits and look-alikes) is refused only when it is
  said of the plugin itself:**
  1. it is the text's first word, or stands alone as a sentence
     ("Official Git tools", "Verified.");
  2. it is within two words of a word for the plugin, in either order, with
     no sentence punctuation between ("verified plugin", "official Git
     extension", "cliente oficial", "公式 Git 拡張", "공식 Git 플러그인"):
     a short per-language list in the data file (plugin, extension, add-on,
     integration, client, app, tool, theme, package, version, release,
     build, and their equivalents). Here the ambiguous words count too
     (已认证插件, 認証済みプラグイン), since the neighbour settles the
     meaning, and 公式 needs no kana;
  3. it directly follows a word that says it of the subject ("is", "are",
     "now", "been", "fully", "officially", and equivalents): "is verified",
     "now official";
  4. it is beside "zeron", "the store" or "the plugin store" (the claims
     rule's reach, kept);
  5. the glyphs, anywhere, as now.
- **A negation directly before lifts 1 to 3** (not, no, non, não, nicht,
  не, 非, 비): "not official", "cliente no oficial", "非官方客户端" pass, as
  "unofficial" always did. It does not lift 4 or 5.
- **A standing word after "zeron's" must not catch ordinary prose:**
  "adds a button to Zeron's built-in terminal" passes. "made" and "built"
  count only directly after a bare "zeron" ("Zeron-made", "Zeron built"),
  never after the possessive and never as "built-in" / "built in".
- **The measure:** on the identity lane's corpus, no honest description is
  refused, and every dodge that says the mark of the plugin itself is. A
  text that passes may still be untrue ("the official Linear integration"
  from someone who is not Linear): that is for a reviewer and a report, not
  for this rule, and the page still says "Not verified yet".
- **Refinements from the identity lane's reading, before the build:**
  - A mark word directly followed by a word that gives it an object
    (against, on, with, for, in, from, under, and equivalents) is describing
    a test or someone else's thing: it does not count under 1 to 3
    ("Verified against Node 22", "is verified on macOS 15"). "by" lifts too,
    unless what follows is the publisher speaking of itself or an authority
    (us, our, the team, staff, experts, reviewers, and equivalents).
  - Under 2, a proper noun between the mark word and the word for the
    plugin lifts it ("the official Slack app", "公式 Slack アプリ").
  - 3 also reads lists and contractions ("safe, fast and verified", "It's
    verified", "C'est officiel") and words of degree (completely, totally,
    truly, 100%).
  - The words for a plugin include what plugins are called (editor,
    previewer, viewer, formatter, linter, bridge, connector, helper,
    wrapper, bot, widget, panel, and equivalents).
  - The first word is read after any leading emoji or punctuation.
- **This rule is a filter, not the judge.** It cannot know a sentence's
  subject, and it will not be made to try harder than this. The lists are
  the engine and identity lanes' to settle between them; the coordinator
  rules only where they disagree. The measure on the identity lane's corpus
  (166 honest, 105 dodges): at most 3 honest texts refused and at most 10
  self-claims passing, each one listed with its reason. A reviewer reads
  every version, and a false claim in a summary is a reason not to verify.
  The refusal's sentence names the word and says how to reword.

## The merged build's review (identity lane, on 9dfc8e89d0b0)

- **An agent never changes plugins on another device.** A forwarded call
  that installs, updates, reinstalls, removes, turns a plugin on or off,
  or changes its pre-release or update preference is accepted on the
  target only when the call was the person's on the device that sent it.
  The sender says so in the forward, the target refuses the call
  `needs_person` otherwise, and an agent's MCP token can never produce
  that claim. The person's own device switcher keeps working.
- **An agent never replaces an installed store plugin by any route**:
  store, file or link (`needs_person`), and never reinstalls one.
- **No mark on a taken-down version.** A take-down event for the version
  a device runs sets that install record's `verified` to false, whatever
  its order with a restore; a blocked version shows no mark. A restore
  brings nothing back (a restored version is unverified until staff
  verify it again, as the edge already rules).
- **An update installs only an installable version.** The re-fetched
  record must be `listed`, not yanked or superseded, or the update is
  refused with its reason. With the store unreachable, a kept package is

- **The feed cursor is bounded.** A device keeps `after` no greater than
  the answer's `head`; a cursor past `head` is a reset. An entry in

  closed).
- **A version is at most 32 characters**, everywhere (this changes
  amendment 3's 128): publish refuses a longer one, so the store, the
  app's link and consent sheet, and the site's links agree.
- **The version link arms its buttons every time it lands**, not only
  when its page first mounts: a second link to an open page waits

- **Smaller:** the consent window says when the publisher changed, as the

## A deploy key is made where the person is, and shown once (Wing, Nov 19)

The site asked people to make a key on their computer and come back. That
is not how anyone expects this to work. **New key on the site makes the key
and shows its secret once**, as the app already does:

- **New key** opens a form: Name, Ends, Can publish (all your plugins, or
  the ones chosen). Create asks for a fresh sign-in (the step-up
  `for: "deploy_key"`), then:
- **The key pair is made in the browser** (WebCrypto Ed25519; where a
  browser lacks it, a pinned, audited Ed25519 implementation shipped with
  the site, never fetched from elsewhere). The page signs proof v2 with it
  and sends only the public key, the proof and the scope to the edge
  (`POST /store/v1/me/keys`, unchanged). **The secret never leaves the
  browser and is never stored**, by the site or the edge.
- **The secret is shown once**, whole, in the site's code block with Copy,
  in exactly the `zpk_…` form the CLI's `key create` prints and the publish
  action reads from `ZERON_DEPLOY_KEY` (byte-for-byte: a key made on the
  site publishes from CI exactly as one made by the CLI). "I've copied it"
  closes it; after that the page lists the key by name and short id and can
  only revoke it. Lost means revoke and make another, and the page says so.
- **The step-up from a web session:** the site re-authenticates the person
  (a fresh WorkOS sign-in) and the edge mints the single-use step-up token
  for that web session, as it does for a device.
- The app and the CLI keep making keys as they do. All three produce the
  same kind of key.

## Deploy tokens replace deploy keys (Wing, Nov 19)

Wing chose a plain token, as npm, PyPI and crates.io use, over a key pair.
This **replaces** the deploy-key sections above (amendment 44's key pair,
proof v2, and the browser-made key in c778f4d6f). Nothing has shipped, so
there is nothing to stay compatible with.

- **Words:** "deploy token" in the app, the site, the CLI and the guide.
  CLI: `zeron plugin token create | list | revoke`. CI reads
  `ZERON_DEPLOY_TOKEN`; the publish action takes it as its input.
- **The token:** `zdt_` + 32 random bytes from the edge's CSPRNG, base62,
  + a 6-character checksum (CRC32 of the rest, base62), so leak scanners
  can recognise it and a typo fails fast. The edge returns it **once**, in
  the create answer, and keeps only its SHA-256 and a short id (the first 8
  characters after `zdt_`). Never logged, never in an error, never in the
  audit row (the short id is).
- **Create:** `POST /store/v1/me/tokens {name, scope, expires?, stepUp}` →
  201 `{token, id, short, name, scope, expires_at, created_at}`. A session
  only, with a fresh sign-in (step-up `for: "deploy_token"`, single use), from
  the app, the CLI or the site; the edge mints that step-up for a web
  session too. Scope, its fixed-at-creation rule, `owner_since`, 1–50 ids,
  20 live and 10 a day, the refusals: as for keys.
- **List / revoke:** `GET /store/v1/me/tokens` (no secret, ever), `DELETE
  /store/v1/me/tokens/:id`.
- **Publish with it:** `Authorization: Bearer zdt_…` on the publish request
  from CI. The edge checks the checksum, finds the hash, and refuses unless
  the token is live, unexpired, the plugin is in its scope and the account
  owns it now; a token never publishes a plugin's first version. Every
  refusal is the same 401/403 shape whether the token is unknown, revoked
  or out of scope, with no timing difference worth a probe (compare hashes
  in constant time).
- **No author signature from CI.** A version published with a token is not
  signed by the author's key. The edge records `via: "deploy_token"`, the
  token's name and short id, and the package's SHA-256. A device installing
  it from the store trusts the store's record (publisher, version, hash,
  verified) exactly as it already does for store installs, checks the hash,
  and shows the publisher as the author: **such a version is never "Unknown
  author"**. Packages published from a device stay signed as now.
- **Notices, last used, transfer:** as for keys: every token publish raises
  the owner's notice with the token's name; a plugin that leaves the
  account leaves every token's scope for good.
- **Removed:** the key pair, proof v2, device-made keys, the site's
  browser-made key, `zpk_`, and their vectors. The shared vectors gain the
  token's format and checksum cases instead.
- **The token's bytes** (engine lane, Nov 19): alphabet `0-9A-Za-z` in that
  order; the 32 bytes as a big-endian integer in base62, left-padded with
  `0` to 43 characters; checksum CRC-32 (zlib/PNG) of the ASCII of `zdt_` +
  body, base62, left-padded to 6; the token is 53 characters,
  `^zdt_[0-9A-Za-z]{49}$`; the short id is the first 8 after `zdt_`, and the
  only part of a token any page, list, notice or log shows; the stored hash
  is the SHA-256 (hex) of the whole token. The shared vectors hold it.
- **Token shapes as built** (engine lane's proposal, accepted): create 201
  `{token, id, short, name, scope, expires_at, created_at}`; list
  `{tokens: [{id, short, name, scope, expires_at, created_at, last_used_at,
  revoked_at}]}`; revoke `DELETE /me/tokens/:id`. A token version's public
  `VersionInfo` and offer carry `via: "deploy_token"` and `key: null`; the
  owner's view carries `deploy_token: {id, short, name} | null` in place of
  `deploy_key`. A token publish sends the package unsigned with only the
  bearer; refusals on publish: 401 `invalid_token` (unknown, revoked,
  expired, a bad checksum) and 403 `token_not_allowed` (a live token out of
  scope, not owned, or a first version); a bearer token on any other route
  is not a session: 401 `session_required`. The device
  takes an unsigned package **only from the store and only when its record
  names no key**, trusts it by the record's content hash now and on every
  scan, and names the store's publisher as its author; an unsigned package
  from a file or link stays "Unknown author" as today. App IPC:
  `ListDeployTokens`, `CreateDeployToken {name, scope, expires?}` (after
  `StepUp {for: "deploy_token"}`) → `{ok, token, secret}`,
  `RevokeDeployToken {id}`; `store_notices` carry `via` and `token_name`.
- **A token publishes and reads nothing** (Nov 19). `GET /store/v1/me/plugins`
  and every other `/me/*` route answer a bearer token 401
  `session_required`, even scoped to the token's plugins: the owner's view
  holds decline notes, unlisted plugins and token names, more than a CI
  secret should read. The CLI's pre-publish "is this newer" check reads the
  plugin's public versions (`GET /store/v1/plugins/:id/versions`, no auth);
  an unlisted plugin falls through to the store's `not_newer`. `status` with
  only a token says it needs you signed in.

## Templates in the store (Wing, Nov 24)

A template is published, browsed, installed and updated beside plugins. It
is the existing signed package (`zeron-template:v1`, its own signing domain
`zeron-template:v1\n`, `template_packages.rs`). It has no permissions: it
runs as Zeron itself. Everything above holds for a template unless this
section says otherwise. The engine lane drafted this section. Its open
choices are the coordinator's rulings of Nov 24, each following Wing's
earlier rulings for plugins; Wing can overrule them.

- **The kind.** Every store item has `kind: "plugin" | "template"`, fixed
  when its id is claimed. `PluginCard`, the detail, `VersionInfo`, an offer,
  a queue row, `/me/*` items and `store_notices` carry it. The names stay:
  a template's card is a `PluginCard` with `kind: "template"`.
- **One namespace.** Ids of both kinds are one set, with one id rule
  (`^[a-z0-9][a-z0-9-]{1,39}$`), and one set of claim rules, reservations,
  `id_too_similar`, reserved `zeron*` ids and `SITE_IDS`. A template can't
  claim a plugin's id, nor the reverse, and a reservation holds an id for
  either kind. Zeron's official templates' ids (`zeron-v2`) are already
  reserved by `zeron*`.
- **The edge's storage.** The `plugins` table is the one table. Its `kind`
  column's check widens to `('plugin', 'template')`, and `id` and
  `skeleton` stay unique across both. That gives one namespace with no
  check across tables.
  - **Migration `0003_template_kind.sql`** (the edge's) rebuilds
    `plugins`, because SQLite can't alter a check. Staging holds data, so
    the "one schema file" rule no longer applies. The rebuild:
    - keeps `seq`, because the FTS5 `plugin_search` is keyed by `rowid =
      plugins.seq`. The copy names every column, 0002's `cover` included;
    - runs under `PRAGMA defer_foreign_keys = on`, because
      `versions.plugin_id` references `plugins (id)`;
    - recreates the four indexes (owner, popular, updated, new).
  - **`takedown_events` gains `item_kind TEXT NOT NULL DEFAULT 'plugin'`**
    (an added column, no rebuild), written with the event. It can't be
    read from `plugins` later, because a released id's row is gone.
  - **`versions` is not rebuilt.** Its plugin-only columns are `NOT NULL`,
    so a template version stores `icon = ''`, `categories = '[]'`, an
    empty consent item, and `engines_zeron = '>=' + zeron_version` (so the
    update filter is reused unchanged). The card, the detail,
    `VersionInfo` and an offer map these by kind: `icon: null`, no
    permissions, `added` and `removed` `[]`. `relist` sets `cover` by kind.
  - **Every query reads the kind.** `LISTED` carries it, so no query can
    miss it, and so does every `FROM plugins` query. A plugin route reads
    `kind = 'plugin'`, a template route `kind = 'template'`, and a
    store-wide route the `?kind=` it was given. That covers lists, search
    (FTS is one table), `?author=`, featured, `sort=verified`, `/stats`,
    `/categories`, `/keywords`, `/me/*` and each side of `/updates`. A
    template never shows where a plugin is asked for, nor the reverse.

### Routes

- **A mirrored prefix, `/store/v1/templates`,** served by the same
  handlers, each given the kind:
  - `GET /templates` (the catalog, with the same query) and
    `GET /templates/:id`;
  - `…/:id/versions` and `…/:id/versions/:version`;
  - `…/:id/versions/:version/package` (the `.zeron-template`);
  - `…/:id/files/:version/:path`;
  - `POST …/:id/versions` (publish), `…/installed` and `…/reports`;
  - `POST …/:id/versions/:version/yank` and `…/unyank`;
  - `GET /me/templates` (the owner's view, the shape of `/me/plugins`:
    `{publisher_id, templates}`).

  An id of the other kind under either prefix is 404 `not_found` (devices:
  `not_in_store`), as an unknown id is, with one exception: a publish
  (`POST …/:id/versions`) to the wrong prefix by the id's owner is 409
  `wrong_kind` ("x is a plugin" / "x is a template"). Anyone else
  publishing to the wrong prefix gets 404 `not_found`, so nothing leaks.
  Under the id's own prefix, another account's publish stays 403
  `id_taken`, as now.
- **Why a prefix and not `?kind=`:**
  - routes.ts dispatches on `parts[2]`, so the kind becomes one argument to
    each handler;
  - `?kind=` would make `/plugins/:id` answer a template;
  - the site's pages are `/plugins/<id>` and `/templates/<id>`, one to one;
  - a device asking for a plugin can never be handed a template.
- **Cache keys and purges take the kind.** catalog.ts and purge.ts build
  their keys from literal segments, not from the path, so the kind is an
  argument to the key builders:
  - every list key (`cacheKey([kind's segment], params)`), `firstPageKeys`,
    `STATS_KEY`, `CATEGORIES_KEY` and `keywordsKey` take the kind;
  - per-id keys (`[…, id]`, `versionsPageKey`, `versionKey`) can't collide,
    since ids are one namespace;
  - `purgeCatalog(db, id, …)` purges that id's kind's first pages, stats,
    categories and keywords.

  cache.ts itself is unchanged.
- **Store-wide routes stay single and take `?kind=plugin|template`,
  default `plugin`,** so nothing that calls them now changes:
  - `GET /stats` → the same shape (`plugins`, `verified`, `new_7d`), counted
    over that kind;
  - `GET /keywords` over that kind;
  - `GET /categories`: for templates, `{categories: []}`, with or without
    `?top=`.

  These have no id, so a prefix buys nothing there.
- **The take-down feed is one feed.** Events add `item_kind: "plugin" |
  "template"` (their `kind` already means `take_down | restore`). A device
  matches a template event only against templates it installed from the
  store.
- **The update check is one request.** The ask adds `templates: [{id,
  version, hash}]` beside `plugins`. The answer adds `template_updates:
  [Offer & {verified_update?}]` beside `updates`. Entries in `blocked[]`
  carry `item_kind`. `hash` is the store record's content `hash` of the
  version as installed, not of the files as they are now (a template can
  be edited where it is installed: see the install section). One limit
  covers both lists together: `max_update_items` (200), which replaces
  `max_update_plugins` in the data file. A template asked about under
  `plugins`, or a plugin under `templates`, is answered as an unknown id:
  never offered, never blocked.
- **Staff:**
  - The queue holds both kinds; rows carry `kind`, and `?kind=` narrows it
    (both kinds by default).
  - Routes that take only an id (`/admin/versions/:id/:version` and its
    actions) take either kind. `GET /admin/versions/:id/:version` answers
    `kind` at the top.
  - The routes under `/admin/plugins/:id/…` (take-down, remove, restore,
    feature, suspend, transfer, release) are mirrored under
    `/admin/templates/:id/…`. An id of the other kind there is 404, for
    staff too; the staff pages always link the right prefix.
  - The operator route `/admin/deploy-tokens/revoke {pluginId}` keeps its
    field's name, which holds an id of either kind.
  - Reports take the same `report_reasons` for templates.
- **Deploy tokens:** `deployTokenMayCall` also allows `POST
  /templates/:id/versions`, and nothing else.

  `<id>` is an installed template of yours; `<folder>` is a template laid
  out as its folder is (`zeron-template.json`, its app files, `preview.png`,
  `README.md`, `CHANGELOG.md`, `screenshots/`; `.base.json` is never
  carried).
- **The package** is `.zeron-template`, unchanged in format. The export
  now also carries the store's files (README, changelog, screenshots: see
  the listing) and the manifest's listing fields, all signed. An older
  Zeron reading such a package installs it as now: the extra manifest
  fields are kept, and the extra files are written into the folder,
  where nothing loads them (an older Zeron counts a changed changelog as
  changed code, so it asks).
- **Deploy tokens publish templates.**
  - The same scope list, ids of either kind. `all` covers both kinds,
    including those first published later.
  - A token never publishes an id's first version.
  - A token publish is unsigned (`via: "deploy_token"`, `key: null`), and
    devices take it by the record's content hash, as for plugins.
  - The tokens CLI stays `zeron plugin token …` (already shipped in the
    guide and the action); its help says a token covers templates too.
- **The publish action** finds the kind from the folder:
  `zeron-plugin.json` publishes a plugin, `zeron-template.json` a template,
  and both or neither is a set-up error (exit 2). It has no new input.
- **Refused on publish, a template's own rules:**
  - a protected path (`PROTECTED`, folded as on the device): 400
    `protected_file`, with the path. The device leaves these out when it
    installs; the store refuses them so that nobody publishes one;
  - a manifest member `builtin_theme` or `builtin_template`: `bad_listing`
    (these marks are the app's own);
  - a file Zeron won't write (`templates::inside`): `bad_package`;
  - a package signed in the plugin domain: `bad_package`;
  - otherwise the same sizes (`MAX_FILES`, `MAX_BYTES`,
    `MAX_PUBLISH_BYTES`), strict semver, the version at most 32
    characters, the ordering rule, superseding, and the hourly, daily and
    new-id limits, counted across both kinds.
- **The content hash** (a record's `hash`) is `signing::content_hash` over
  the signed manifest (without its signature) and every file the package
  carries, `preview.png` included: the same function as for plugins, over
  the template's files.

### The listing

- **Manifest fields** (in `zeron-template.json`, all signed):
  - required: `id`, `name` (≤ 64), `description` (≤ 300), `version`
    (strict semver), `zeron_version` (strict semver: the Zeron it was made
    from);
  - optional, with the plugin rules and limits: `keywords` (≤ 8, ≤ 32
    each, the keyword rule), `screenshots` (≤ 8, PNG or JPEG package
    paths), `homepage`, `repository`, `license`;
  - no `icon`, `engines`, `permissions`, `commands`, `services`, `tools`
    or `categories`. A template's manifest has none of these, and the store
    refuses them (`bad_listing`).
- **No `categories` for templates** in this first version: plugin
  categories don't fit them (every template is "appearance"), and keywords
  are the facets. A `categories` member is refused (`bad_listing`), and
  `GET /categories?kind=template` answers `{categories: []}`.
- **Files:**
  - `preview.png` is required (`missing_listing`, field `preview`) and is
    the card's cover: a template's `PluginCard.cover` is always
    `"preview.png"` (the first-screenshot rule is for plugins), and its
    `icon` is null. It must be a PNG the store serves, else it is
    `bad_listing`, field `preview`:
    - at most `max_preview_bytes`;
    - the PNG signature (the device's check, as for a screenshot);
    - on the edge, it also passes the image check that screenshots pass
      (`pictureType` is `image/png`: the picture rebuilt, at most
      `MAX_DIMENSION` px a side), so a published cover is never a 404;
  - `README.md` is required and is the store page (`missing_readme`). The
    README Zeron writes when it makes a template is refused as missing:
    the data file holds its fixed sentence (`template_readme_stub`), and a
    README containing that sentence is refused;
  - `CHANGELOG.md` gives each version's notes (`no_notes`), as for plugins;
  - screenshots live under `screenshots/`.

  README, CHANGELOG, `preview.png` and `screenshots/` are listing files.
  They are carried and installed, but are never app files: they are
  outside `own_files`, never loaded, and never counted as a code change.
- **The mark rules apply unchanged** to a template's name, description
  and keywords. The words "verified" and "official" stay strict in a name
  and in keywords, and in a description are refused only when said of the
  template itself. The words for a plugin add "template", "theme",
  "layout", "interface", "skin" and their equivalents in the listed
  languages.
- **No permissions; a fixed fact instead.** A template's card, detail,
  version and offer carry no permission list, and its `added` and
  `removed` are always `[]`. Wherever the app or the site shows a
  template (card, page, version page, the consent window, the update
  sheet, an installed row), it always says "Runs as Zeron itself": it can
  do anything Zeron can, with all of Zeron's powers. It is not a field: the
  kind is the fact, so no record can leave it out. The app and web lanes
  choose the exact words, in both languages, together.
- **Compatibility.** A plugin is filtered by `engines.zeron`; a template
  has `zeron_version`, the Zeron it was made from (a file that fails falls
  back to Zeron's own). The store reads it as `>=zeron_version`, so a
  template made from a newer Zeron is never offered to an older one. There
  is no upper bound: the app already says "made for an older Zeron".

### Review

- **A reviewer sees every file**, each as code: a template has no
  manifest summary to stand in for reading. They see the diff against
  `base` (the newest verified other version) for every file, pictures side
  by side, and the README and changelog as text. The staff page says that
  the template runs as Zeron itself.
- **The states and reasons are those of plugins:** verified, not verified
  yet, and declined (shown to its author only), plus take-down, remove,
  restore, the superseding rule and the queue's two rows per id. Reasons
  and reports work as now. Featuring needs the newest version verified.
- **Public at once, as a plugin.** No permission line limits what a
  template does, but a template is public at once, unverified, as a
  plugin is (amendment 45), and is not held until it is verified.
  Installing one always asks (see the install section), and a plugin that
  runs programs is as powerful.

### Install from the store

- **The app's flow.** A template's store page → Install → the engine
  fetches that version's record and package. The install is checked as
  for plugins:
  - sha256 and the content hash match the record;
  - the key matches the record's, or both are null;
  - a signed package under a record with no key is `store_mismatch`;
  - a package signed in the plugin domain is refused.

  The template then waits in `.pending/` for **Zeron's own consent
  window**, which always asks for a store template, verified or not, yours
  or not. That window says it runs with all of Zeron's powers; it shows
  the store's publisher (never "Unknown author"), whether this version is
  verified (from the record fetched now), and the verified alternative
  when this version isn't. Allowed, the template is installed. Installing
  never switches the interface: Use stays its own action, as today.
- **Agents:**
  - An agent may ask for a verified version (`verified_version`, or a
    named version that is verified); it waits in the consent window for
    the person.
  - Anything else is `needs_person`.
  - An agent never updates or replaces an installed store template.
  - A forwarded call needs the person's claim (`BY_PERSON`).
- **The link:** `zeron://open/template/<id>` opens the template's store
  page, with `?version=<v>` and `ARM_MS` exactly as for plugins. The
  site's Install opens it.
- **Origins sit side by side.**
  - An installed template has one origin, the one it came from: a file, a
    link, a release, or the store (`.imported.json`'s `source`, `kind:
    "store"`, with the record it was installed from).
  - A store template checks only the store, through the update check and
    the take-down feed. A file, link or release template checks only where
    it came from, as today (the same key, a newer version). Neither takes
    the other's version, even under the same id and the same key.
  - Installing from the store an id that is already installed from
    elsewhere installs beside it (`<id>-2`), as an import does now, and
    never replaces it. The store page says that you already have it from
    that origin.
- **Updates from the store follow the plugin rules:**
  - the update preference (`newest` | `verified`);
  - an unverified update is always its own action and always asks;
  - "update all" takes only verified updates;
  - an update must be `listed`.

  The template rule is kept too: a version whose code differs from what is
  installed goes to the consent window (verified or not), and only a
  change of the preview or the listing files installs without asking.
  Since nearly every template update changes code, nearly every one asks.
  An update replaces any edits made on the device, and the window says so
  when the installed files differ from the version as installed.
- **The mark on an installed template** comes from the record it was
  installed from, as for plugins, and it shows only while the template's
  files hash to that record's content hash. A template edited on the
  device shows "Changed on this device" and no mark.
- **A take-down blocks by id and version**, whatever has been edited
  (fails closed). A blocked template can't be used. If it is in use, Zeron
  switches to its own interface at once and says why. A restore brings
  nothing back automatically.

### The shared files (the engine's generator)

- **The data file adds:**
  - `kinds: ["plugin", "template"]`;
  - `template_format: "zeron-template:v1"` and
    `template_payload_prefix: "zeron-template:v1\n"`;
  - `template_protected` (`PROTECTED`);
  - `template_listing_files` (`README.md`, `CHANGELOG.md`, `preview.png`,
    `screenshots/`);
  - `template_manifest_fields` (required and allowed) and
    `template_refused_members` (`builtin_theme`, `builtin_template`,
    `permissions`, `commands`, `services`, `tools`, `engines`, `icon`,
    `categories`);
  - `template_readme_stub`;
  - the words for a template, added to the mark rule's words for a plugin;
  - in `limits`: `max_preview_bytes` (4194304, 4 MiB) and
    `max_update_items` (200, in place of `max_update_plugins`).
- **The vectors add:**
  - template signature cases: a valid one; a plugin-domain signature
    checked as a template's, and the reverse, `bad_signature`; files
    differ; unsigned;
  - template content-hash cases;
  - `template_packages`, each with its result: valid; unsigned from the
    store (taken only when the record has no key); signed under a record
    with no key; a protected path (`Screens/Plugins/x.luau`, `account./x`
    and other folds); a file Zeron won't write; a builtin mark; too many
    files; another format;
  - `template_listing` cases: no preview; a `preview.png` that isn't a PNG
    (a JPEG, text); one over `max_preview_bytes`; the stub README; a
    refused member; the mark words with "template" and "theme" beside
    them; and honest ones;
  - a package of each format checked as the other kind's (what each
    prefix refuses);
  - one token-scope case that names a plugin and a template.

  The edge takes both files unedited.

### Kinds where pages link by id (coordinator, Nov 24)

- **A report row's `plugin` is `{id, name, kind}`, and an audit entry that
  names an item carries `item_kind`** (its action words are its own), null
  when the entry names none. The staff pages link by it: an id of the other
  kind under a prefix is 404 for staff too.
- **A deploy token's chosen scope and its `last_used_plugin` carry no kind.**
  The site looks them up in `/me/plugins` and `/me/templates`; an id that is
  the author's no longer is shown as its id.
- **Compatibility is one field for both kinds:** `engines: {zeron: ">=x"}` on
  a detail, a version and a review record. A template's comes from its
  `zeron_version`, which its signed manifest keeps.
- **The site serves a template's files at `/templates/:id/files/:version/:path`,**
  from the edge's template prefix. Both kinds draw from the same page
  components, given the kind; no page is copied.

### Templates: after the trust review (coordinator, Nov 24)

These win over anything above them.

- **An installed package is known by its record, never by its key.** A
  null-key `.imported.json` (a deploy token's publish) goes through list,
  decide, update, block and the keep sheet like any other. `write_folder`
  strips `builtin_theme` and `builtin_template`. Take-down, update and the
  mark match by the **record's store id**, never the folder's name (`foo-2`).
- **A take-down is enforced before any template code runs.** The app records
  the block beside its approvals and reads it before composing anything (the
  launch stamp and the warm path too), forgets the approval, and switches by
  safe mode's path. Use, create-from and export refuse a blocked template. A
  block holds by id and version **and by the content hash**, so a copy of the
  same files, and a file or link import of them, is blocked too. A kept
  template can undo its own block: this guards the honest case, and says so.
- **Publishing and a new token, while a template that isn't Zeron's is in
  use:** the last step (Publish; showing the new token) is asked in Zeron's
  own consent window. With Zeron's interface nothing changes. Every publish,
  from a device too, raises the author's notice.
- **What installs without asking** is a verified update from the same
  publisher whose only differences are listing files and the manifest's
  `version`. An unverified update, a changed publisher, or any other manifest
  change always asks.
- **One predicate for listing files** (`README.md`, `CHANGELOG.md`,
  `preview.png`, PNG and JPEG files under `screenshots/`) decides the digest,
  composing, `own_files` and `changes_code`, in the engine and the app. Any
  other file under `screenshots/` is refused (`bad_listing`) and never
  composed.
- **The manifest is an allow list:** a member outside
  `template_manifest_fields` is `bad_listing`; `author` is never read from an
  imported manifest.
- **The kind is part of the commit:** a publish's insert has `kind = ?` in
  its own condition.
- **A wrong prefix:** 409 `wrong_kind` to the id's owner; anyone else's
  publish is 403 `id_taken` under either prefix. `token_not_allowed` answers
  before either.
- **Deploy tokens: `all` names its kinds.** `all_kinds` is `["plugin"]` or
  `["plugin", "template"]`, chosen when it is made; a token made before this
  is `["plugin"]`. Chosen ids are of either kind.
- **Agents:** no deleting a store-installed template. Every template method
  stays `local_only`. A file or link import says "from a file, not from the
  store" in the consent window.
- **The mark on an installed template** hashes every file in its folder but
  the engine's own dotfiles, when it is shown. A fresh install hashes to its
  record (tested). `decide` approves the digest of the package shown, not one
  read again from the disk.
- **Reviewing a first version:** each file is marked the same as Zeron's,
  changed, or new, against Zeron's own files at its `zeron_version` (hashes
  the generator writes for each release, never the author's word). An unknown
  `zeron_version` says so and shows every file.
- **`template_protected` only grows:** the store refuses the union of every
  released version's list, and the generator's test fails when one is dropped.
- **The feed:** the cursor moves after both kinds are applied; an unknown
  `item_kind` is skipped, a missing one is a plugin; a reset rebuilds both.
  A device keeps its block when an id is reclaimed as the other kind.
- **`preview.png`** is a still PNG (no `acTL`). The mark is drawn outside it,
  with "Not verified yet" always in words. While a template runs, only the
  consent window's mark is proof.
- **`SITE_IDS`** is the union of the reserved paths of both prefixes.
- **The mark words:** out, `modèle(s)`, `modello`/`modelli`, `modelo(s)`,
  `スキン`, `diseño`. In, 佈局 介面 範本 皮膚, `インターフェース`,
  `インターフェイス`, `인터페이스`, `gabarits`, `habillages`, `interfacce`.
