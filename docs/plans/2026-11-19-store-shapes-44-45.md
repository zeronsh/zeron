# Store shapes for amendments 44 and 45

The one copy. The edge and engine lanes drafted these shapes together and
their drafts crossed; the coordinator ruled that this text is the contract
(the edge store lane's final page, plus the coordinator's rulings at the
end). Where a lane's message differs from this file, this file is right.

Times are milliseconds. A record is `{hash, sha256, bytes, key}`.

## Versions

- **States:** `status` is `listed | yanked | taken_down | removed`.
  - `taken_down` is staff's call: harmful, and blocked on devices.
  - `removed` is staff's call: not harmful, not blocked.
- **What the public sees:** `listed` and `yanked` only. The package route
  serves both. A yanked version is never an update offer, only a reinstall.
- **Ordering:** a publish must be later than every existing version, in any
  state. The data file's `newer_rule` says so.
- **An unverified version stops taking new installs when a newer one is
  published.** When a version is listed, every older listed version that is
  not verified becomes `yanked`, with `yanked_by: "superseded"` and the
  version that superseded it (a release supersedes older releases and
  pre-releases; a pre-release supersedes older pre-releases only). Its
  author cannot unyank it. Verified versions are untouched: every verified
  version stays installable, and so does the newest version whether verified
  or not. So no version can sit installable and unread behind a newer one.
  A superseded yank is for good: a take-down, a remove or an author's yank
  of a newer version brings nothing back, and the author publishes again.
  If that leaves a plugin with nothing installable, it leaves the lists.
  - **Verifying a superseded version clears its superseded yank** (every
    verified version is installable); an author's own yank stays.
  - **A restore applies the rule again:** a restored version comes back
    unverified, and straight to `yanked_by: "superseded"` when anything
    newer on its line is listed.
  - **One write:** the "later than every version" check, the insert and the
    superseding are one D1 batch, after the package is stored, so a publish
    that fails supersedes nothing. A retried publish of the same bytes
    answers that version's current state and changes nothing.
  - Superseding does not look at `engines`: an unverified version that
    needs a newer Zeron can leave older Zerons with nothing to install until
    it or an earlier one is verified. That is the author's to weigh.
- **Public `VersionInfo`:** `{version, status, published_at, notes, engines,
  yanked, prerelease, key, hash, sha256, bytes, verified: bool,
  verified_at: ms|null, via: "device"|"deploy_key"}`. `verified` is always
  present, and readers require it.
- **Owner and staff add:** `review: {decided, decision:
  "verified"|"declined"|null, reason?, message?, decided_at?}` and `checks`.
  The public never sees "declined".
- **Every version:** `GET /store/v1/plugins/:id/versions?cursor&limit` →
  `{versions, total, next_cursor?, prev_cursor?}`, listed and yanked, newest
  first.
- **One version:** `GET /store/v1/plugins/:id/versions/:version` → that
  `VersionInfo`, else 404 `not_found` (devices: `not_in_store`).

## Cards and detail

- **`PluginCard` gains** `verified` (its `version` is verified) and
  `verified_version: string|null`. `version` is the newest listed version, a
  release before a pre-release, verified or not.
- **Detail:** `versions` is the first page (5), plus
  `versions_next_cursor?`; `package` is `version`'s record; a device installs
  `verified_version` through the one-version route. There is no
  `verified_package`.
- **The mark is the store's alone.** A version once verified stays verified;
  only a take-down ends it, and a restored version comes back unverified.
  The listing rules refuse a name or summary that claims the mark (the words
  "verified" or "official", a check-mark glyph). Where a person decides or is told what
  they are running (the consent sheet, the update sheet, an installed
  plugin's row), a device draws the mark only from the record it installs
  from, fetched at install time: never from a card, a remembered offer, the
  manifest or anything an agent passes. Where it only shows the catalog
  (Browse's rows, a plugin's store page), it shows what the store's answer
  says, fetched for that visit and not kept past it.
- **Names too like another's.** Claiming an id one edit, or one confusable
  letter, from an id another account owns with 100 installs or more is
  refused `id_too_similar`; staff can allow it by reservation.
- **Catalog:** `?verified=1` narrows it; `?featured=true` holds only plugins
  whose newest version is verified; featuring a plugin without that is 409
  `not_verified`; `?author=<username>` lists one publisher's plugins: checked against
  the username rule and lowercased before it is a cache key, and an unknown
  username answers the same empty list as one with no plugins.
- **Categories** carry `count`, and `GET /store/v1/stats` answers
  `{plugins, verified}`. Both count exactly the set the lists show (never a
  taken-down, removed or suspended plugin, nor one whose only versions are
  yanked) and are purged with the lists.

## Publish

- `POST /store/v1/plugins/:id/versions` → `201 {id, version, status:
  "listed", verified: false, checks}`, public at once. The same bytes get the
  same answer.

## Updates and take-downs

- **The update check:** `POST /store/v1/updates`, the ask unchanged
  (`verified_only` per plugin is accepted).
- **Each offer:** the newest listed version newer than the installed one that
  fits `engines` and the pre-release choice: `{id, version, hash, sha256,
  bytes, key, publisher, publisher_id, notes, added, removed, prerelease,
  verified, verified_at}`; `verified_update?` has the same shape, present
  only when the offer is unverified and a newer-than-installed verified
  version exists; `in_review` goes; `blocked[]` is unchanged.
- **The take-down feed:** `GET /store/v1/takedowns?after=<seq>` →
  `{events: [{seq, kind: "take_down"|"restore", id, version, reason?}],
  head, reset?}`. Public, cached 60 s per colo, purged on each event.
  - `seq` is a number the store assigns in the same D1 write that takes a
    version down or restores it, in commit order. A device never sends a
    time; `after` is the last `seq` it applied. A cached answer can only
    delay an event, never skip one. Pages hold at most 500, in `seq` order.
  - The feed keeps 30 days. An `after` older than that, or none, answers
    `{reset: true, head}`: the device runs the full update check (which
    reports blocks on what it has installed, and clears blocks the store no
    longer names) and then continues from `head`.
  - Devices poll every 15 minutes and match events against their installs
    locally, sending nothing about them. The full check stays at 6 hours.
  - A take-down guards the honest case. A plugin that runs programs can
    undo its own block on a device; what stands against a hostile plugin is
    the consent sheet saying that it runs programs.

## Deploy keys (44)

- **List:** `GET /store/v1/me/keys` → `{keys: [{key, name, scope,
  created_at, last_used_at, last_used_plugin, expires_at, revoked_at?}]}`.
  `scope` is `{all: true}` or `{plugins: [ids, sorted, unique]}`.
- **Create:** `POST /store/v1/me/keys {key, name, scope, expires?, proof,
  stepUp}` → 201. Session only, with a step-up `for: "deploy_key"`, used
  once. 1–50 ids, each owned now. Refusals: 400 `{error: "invalid_scope",
  ids?}`; 403 `{error: "not_owner", ids}`.
- **Revoke:** `DELETE /store/v1/me/keys/:key` → `{revoked: true}`.
- **Proof v2:** the key signs `"zeron-deploy-key:v2:" + publisher_id + ":" +
  expiry + ":" + scopeText + ":" + key`, where `publisher_id` is the
  account's opaque publisher id (amendment 33), `expiry` is the key's
  `expires_at` in ms or `never`, and `scopeText` is `*` for all, else the
  ids, each checked against the id rule, sorted by code unit (JavaScript's
  default sort and Rust's string order agree for these), a duplicate refused
  rather than dropped, joined with `,`.
  A proof is good for one account's key with one lifetime and one scope. v1
  is refused. The engine generates the data file (`proof_prefix` v2)
  and the vectors (cases for `*` and for two sorted ids); the edge takes both
  unedited.
- **A signed request may:** `POST /plugins/:id/versions` when the id exists,
  the key's account owns it now, and it is in scope; never a new id (403
  `key_not_allowed`); `GET /me/plugins` (the in-scope plugins it owns);
  nothing else.
- **`/plugin-keys/:key?plugin=`:** verified only when the key is live, the
  plugin is in scope, and the account owns it.
- **Leaving and arriving:** ownership is checked at each use. A plugin that
  leaves the account is removed from every key's scope for good; coming
  back does not restore it. `all` means the plugins the account owned when
  the key was made and those it first publishes later, never a plugin
  transferred in.
- **Limits:** at most 20 live keys an account, and 10 keys made a day.
- **A publish through a key** raises a notice on the author's own devices
  (which key published which version).

## Author and staff

- **Author:** `withdraw` goes; `yank` and `unyank` stay. In `/me/plugins`,
  versions carry `review`, and `listing` is `listed | unlisted | suspended`.
- **Staff queue:** `GET /admin/queue?state=undecided|verified|declined|all`,
  default undecided, oldest first, versions with open reports first. The
  queue holds every undecided version the superseding rule has not yanked:
  at most two rows a plugin, its newest undecided release and its newest
  undecided pre-release when that is newer. A version leaves the queue only
  by a decision or by the rule that yanks it, so nothing that leaves it
  unread can be installed. Each row says how many earlier undecided versions
  it superseded (a reviewer can still open each from the plugin's staff
  page). Items as amendment 40, plus
  `status`, `review`, `reports`. `base` is the newest verified other version.
- **Staff actions:** `GET /admin/versions/:id/:version`; `POST …/verify`
  (from undecided or declined); `POST …/decline {reason, message}` (from
  undecided); `POST /admin/plugins/:id/versions/:version/take-down {reason}`
  (blocks); `POST …/remove {reason}` (does not block). Each needs the version
  listed or yanked, else 409 `invalid_state`.
- **Audit:** `version.publish` (the author is the actor; `detail {via,
  key}`), `verify`, `decline`, `take_down`, `remove`, `yank`, `unyank`, and
  `plugin.*`, `report.*`, `reservation.*` as now.

## Coordinator's rulings

- **Sorts are honest.** Every sort is exactly its own key, verified or not;
  `verified=1` is a filter; search relevance uses `verified` only to break
  ties. Featured is the vetted shelf.
- **The device's update preference** (`store_updates: "newest" |
  "verified"`, device-wide, with a per-plugin override) defaults to
  `newest`: the newest version is offered and staged, marked when not
  verified, with the newest verified one beside it. One constant.
- **Consent:** installing or updating to an unverified store version always
  asks, even when it asks for nothing new.
- **Agents install only verified versions.** A store install by an agent
  takes `verified_version`, or a named version that is verified; anything
  else is refused `needs_person`, whether or not a verified version exists
  (a new plugin nobody has read, a squat, a plugin whose verified versions
  were yanked). An agent never updates an installed store plugin.
- **Updates in bulk never take unverified code.** Any "update all" applies
  verified updates only; an unverified update is always its own action,
  with its own question, and its sheet says when the installed version was
  verified and this one is not.
- **Every publish not made on this device raises a notice** on the author's
  devices: which version, and whether another device or which key sent it.
  The engine keeps it until the app is there to show it, once per version.
- **No cap tied to review speed:** the hourly, daily and new-id limits stay
  as they are.
- **Reports** reorder the queue and never hide a plugin by themselves.

## Names settled while building

- **Restore:** `POST /store/v1/admin/plugins/:id/versions/:version/restore
  {reason}` takes a `taken_down` version back to `listed`, unverified,
  writes a `restore` event and `version.restore` in the audit, and lifts the
  block.
- **The queue row** carries `earlier_undecided: n`.
- **For staff,** `GET /admin/versions/:id/:version` carries `superseded:
  {at, by} | null`, and the plugin's staff page lists each version with it.
- **The publish notice:** the owner's view of a version in `/me/plugins`
  carries `via`, `key` (the signer) and `deploy_key: {key, name} | null`. A
  device tells "another device" by `via: "device"` with a key that is not its
  own, and "which key" by `deploy_key.name`.
- **`id_too_similar`** is measured on the username rules' `skeleton`: a new
  id is refused when its skeleton equals, or is one edit from, the skeleton
  of an id another account owns with 100 installs or more. At claim only.
- **What `all` covers:** a plugin has `owner_since`; it is in an `all` key's
  scope when it was owned when the key was made, or the account claimed it
  and it has never changed hands.
- **Email:** the edge sends none today. The device notice stands alone until
  a provider and a sending domain are decided.
- **From the edge's build (b467e6299):** the publish answer adds
  `superseded: [versions]`; an owner's versions carry `yanked_by:
  "author"|"superseded"` and `superseded {at, by}`; a transfer sets
  `owner_since` strictly later than the claim and than any earlier transfer;
  registering a revoked key again is 409 `key_revoked`, the same key under
  another scope 409 `key_taken`; `/plugin-keys` shows `scope` to the key's
  owner only; the audit has `version.restore`; the staff view of a version
  carries `decisions {verified, declined}`.
- **The schema is one file,** `edge/migrations/store/0001_store.sql`. No
  database existed before it; a database made by hand from the older files
  is recreated, not migrated.
- **`GET /store/v1/me/plugins` answers `{publisher_id, plugins}`,** to a
  session and to a key alike, with plugins or none: a device needs its own
  publisher id for proof v2 before it has a plugin.
- **The mark-claiming rule** (engine 1128fe31c, edge bc60237ba): `bad_listing`
  on a name or description that, folded (NFKC, lowercase, NFKD with
  nonspacing marks dropped), holds a check-mark glyph or the whole word
  "verified" or "official". The edge alone also maps look-alike letters of
  other alphabets first; the vectors hold the edge to `edge_problems` and
  the device's check to `problems`.
- **A cached answer's key is built from the value its handler uses, read
  once.** A take-down feed `after` that is not `^[0-9]{1,15}$` is 400 and
  never cached; a search with no searchable word is keyed as a search.
- **The public `VersionInfo` says why a version takes no new installs:**
  `yanked_by: "author"|"superseded"|null` and, when superseded,
  `superseded_by: <version>`. A plugin's page can then say "Replaced by
  1.3.0 before it was verified" without the owner's view.
- **Look-alikes come from the standard, in one table.** The engine
  generates, from Unicode's confusables.txt (UTS #39), the look-alikes of the
  letters "verified" and "official" use, plus the digit folds, into the data
  file with the Unicode version and the source's hash. The device's check
  and the edge both read it: one rule, one answer (`edge_problems` goes).
  The glyph list gains √ and U+10102.
- **A name or summary cannot say the plugin is Zeron's own unless it is.**
  After the same folding, "by zeron", "from zeron", "zeron team", "zeron's
  own", and "zeron" directly followed by approved, certified, endorsed,
  recommended or staff are refused `claims_zeron`, unless the publisher
  carries Zeron's own badge. The edge enforces it; the device warns.
  "Zeron's own badge" is the publisher's `maintainer` badge: only staff grant
  it, at the edge, and nothing a publisher sends can set it. A device cannot
  know the publisher, so its shared check gives a warning; a publish is
  refused 400 `claims_zeron` with its sentence.
- **What the engine tells a sheet about an unverified store version.** An
  update's item carries `update.verified` (bool), `update.installed_verified`
  (bool) and `update.verified_alternative`; a first install's item carries
  `source.verified` and `source.verified_alternative`, the same name and
  shape in both places: `{version, added, removed, notes?, verified_at?} |
  null` (as the engine built it at acc084360; `added` and `removed` are
  what it asks for against the version being asked about). The alternative is the newest verified version this Zeron can run
  that is not the one being asked about (for an update, newer than the
  installed one), or null. `nothing_new: true` marks an item that asks
  again only because the version is not verified. A sheet's "instead"
  action is the host's (`plugins.install_verified {id, hash}`), which asks
  the engine `InstallVerifiedPlugin {id, hash}` (b1bd30e10): the engine
  reads the version from its own pending item, never from the host or a
  script, fetches that version's record then, and refuses `not_verified`
  unless that record says verified.
- **One sheet for an unverified update.** Installed's Update link stages the
  update and the consent window opens with the warning, the line on the
  installed version ("The version you have, 1.2.0, was verified." when it
  was) and the "instead" action; the store page's update sheet says the
  same. Never two questions for one update.
- **A notice is only for the account's own publishes.** The owner's view of
  each version in `/me/plugins` also carries `publisher_id`: the account
  that published that version, fixed at publish and unchanged by a transfer
  (the id offers already carry in public). A device raises a publish notice
  only for versions whose `publisher_id` is the account's own, the
  top-level `publisher_id` of `/me/plugins`; a version with no
  `publisher_id` is noticed (the safe side). So a plugin transferred in
  brings no notices for its former owner's versions.
- **The link can name a version.** `zeron://open/plugin/<id>?version=<v>`
  opens that plugin's page with that version chosen: its Install acts on
  `<v>`, says so on the button ("Install 1.2.0"), and the page shows that
  version's state. `<v>` must read as a version (the same cleaning as
  anywhere a version is said) or the link opens the page as if it had none;
  any other query key is ignored. Nothing else changes: the page arms its
  buttons after `ARM_MS`, the install asks as any install does, and the
  device takes the mark from that version's record. The web uses it for
  "Install 1.2.0" beside an unverified newest version, and on a version's
  own page.
- **Who does what, in words.** Zeron verifies ("Zeron hasn't verified 1.3.0
  yet", "Verified"); a reviewer reads ("Waiting for a reviewer", "until a
  reviewer has read it", "The reviewer's note"). The three states are
  "verified", "not verified yet" (no decision) and "not verified"
  (declined, to its author only). The app and the web use the same words.

## Claims of being Zeron's, after the identity lane's attack

- **"zeron" is read as the mark words are:** the same folding, look-alike
  table, spacing join and unseen-character removal, before any test below.
- **In a plugin's name, "zeron" is refused unless it is said about Zeron,
  not as Zeron.** Allowed only as the object of a short list of forms kept
  in the data file for the store's own locales (English: "for Zeron", "in
  Zeron", "with Zeron", "on Zeron", "to Zeron"; the Chinese forms beside
  them). Any other use in a name ("Zeron Labs", "Team Zeron", "Zeron Git",
  "Zeron's git", "Zeron-made") is `claims_zeron`, unless the publisher
  carries `maintainer`. A name that leads with the brand reads as ours.
- **In a summary or description, the phrase test stays, wider.** Refused:
  "zeron" directly after a word of origin (by, from, "by the", made by,
  built by; von, par, de, da, di, del, van) or directly before or after a
  word of standing (team, labs, inc, hq, staff, approved, certified,
  endorsed, recommended, made, built; 官方, 公式, 공식). Prose about Zeron
  ("adds a panel to Zeron's sidebar") passes. The lists are in the data
  file; the edge and the device read them.
- **The mark words in other languages.** "verified" and "official" are
  also refused in Spanish, French, German, Italian, Portuguese, Russian,
  Chinese, Japanese and Korean (a short list in the data file), whole words
  for scripts with spaces and as substrings for Chinese, Japanese and
  Korean. This also refuses "no oficial" and "非官方", as "not official" is
  refused in English: the author rewords.
- **A claim does not outlive the badge.** A transfer of a plugin whose name
  or summary would be `claims_zeron` for the new owner is refused (409
  `claims_zeron`) until it is renamed. Revoking `maintainer` from an account
  sets `listing: suspended` on each of its plugins that would now be
  refused, names them in the answer and in the audit, and their installed
  copies keep running.
- **Usernames.** The reserved check reads a username with the digit folds
  (0 for o, 3 for e, 2 for z, 1 for i or l) and with runs of one letter
  collapsed, so "zer0n", "2eron", "zerron" and "zeeron" are refused as
  "zeron" is. A username one different letter away ("xeron", "heron") is
  not refused: the badge, not the handle, is what says a plugin is ours.

## What the site's pages ask of the catalog

- **`GET /store/v1/stats`** also answers `new_7d`: plugins first listed in
  the last seven days, counted over the same set the lists show.
- **`GET /store/v1/categories?top=<n>`** (n ≤ 4) adds `top` to each
  category: its n most installed plugins as `PluginCard`s, the same order
  and set `?category=<id>&sort=popular` gives. Without `top`, as now.
- **`GET /store/v1/keywords?category=<id>&limit=<n>`** (n ≤ 24; `category`
  optional) → `{keywords: [{keyword, count}]}`, the most used keywords among
  the plugins the lists show, most used first, ties by keyword. `count` is
  the number of listed plugins carrying it.
- **`sort=verified`** on the catalog: plugins that have a verified version,
  by when their newest verified version was verified, newest first (ties by
  the stable key, as every sort). A `PluginCard` carries `verified_at`: that
  time, or null when it has no verified version. This is the site's "Newly
  verified" shelf; it is its own honest sort, not a re-ranking of another.
- All of these are public, cached as the catalog is, and keyed on their
  whole query.
- A category's one-line description is the site's own words (not the
  edge's). The device a version was published from is not named anywhere:
  the site says "one of your devices", as the app's notice does.
- **Keywords are held to both rules.** A keyword is read as a name is (the
  same folding, digit folds and `i`/`l`), with "-" as a separator between
  its parts. It is refused when a part, or its parts joined, is a mark word
  (in any of the listed languages that can be written in a keyword's
  letters), and it is refused when any part is "zeron": every plugin here
  is for Zeron, so the word says nothing in a keyword and only ever serves
  a claim. No badge lifts this. Keywords show on cards and in the store's
  own keyword list, so they are part of what the store says.
- **The other-language mark words must not refuse ordinary words.** A word
  goes in the bare list only when its matched form has no common other
  meaning in text about software. Where it has one, the rule narrows:
  - French "vérifié" folds to "verifie", which is also "vérifie" (checks).
    In a name the folded form is refused; in a summary or description only
    the accented participle ("vérifié", "vérifiée", and plurals) is.
  - 公式 is "official" in Japanese and "formula" in Chinese: refused bare
    only in a text that also holds kana.
  - 공식 (official, formula), 认证 / 認證 / 認証 / 인증 (certified,
    authentication) are not refused bare. Unambiguous forms are: 官方,
    已验证 / 已驗證, 已认证 / 已認證, 認証済み, 検証済み, 確認済み, 인증됨,
    검증됨, 확인됨 (the engine lane may correct this list with reasons).
  - Beside "zeron", every one of them is still refused by the claims rule,
    and so are the Chinese words of origin 由 and 来自 in a summary or
    description.
  The vectors carry honest cases that must pass: "Vérifie la syntaxe de vos
  fichiers", "数学公式编辑器", "수학 공식", "身份认证", "認証トークン", "인증
  토큰".
- **Which window asks.** The consent window is the one place a person
  allows an unverified version. From Installed, Update on an unverified
  offer stages it and the consent window opens (0881e0bb3): not the store
  page, not a second sheet. On a store page, the update sheet stays what it
  was, "what's new, and what changes": for an unverified offer its warning
  states the fact, offers the verified alternative, and says that Zeron
  asks before it installs (as its new-publisher callout already says);
  pressing Update there leads to the consent window, which asks. One click
  still never takes unverified code: the update is staged, waiting.
- **An installed version can become verified.** At each update check the
  device also re-reads the record of the version it runs; when that record
  now says verified and names the same package (hash), the install record's
  `verified` becomes true with its `verified_at`. Never the reverse from a
  check (a verified version stays verified; take-downs come by the feed).
  So a row that said "not verified yet" stops saying it once Zeron has
  read that version.
- **Saying a plugin is part of Zeron is a claim too.** Words of belonging:
  built-in (builtin, built in, built into), bundled, included, preinstalled
  (pre-installed), ships (shipped), comes with, native, default, stock,
  core, first-party, part of. In a **name** that holds "zeron", any of them
  anywhere is `claims_zeron` ("Built-in Zeron Git", "Default Git for
  Zeron"). In a **summary or description**, one of them directly before
  "(with | in | into | to | for | of) zeron" is ("ships with Zeron",
  "included in Zeron", "part of Zeron"); "adds a button to Zeron's built-in
  terminal" passes. The Chinese equivalents go beside them (内置, 自带,
  预装, 默认, 原生), chosen by the engine lane with reasons.
- **Japanese and Korean "official", narrowed further:** 公式 and 公認 only
  in a text that also holds kana; オフィシャル always; 공식 only directly
  before 플러그인, 앱, 패키지, 확장 or 버전 (a space allowed); 공인 not
  bare (공인인증서 is an ordinary term).

## The mark's words in a summary: only when said of the plugin itself

The identity lane measured the rule above on 79 honest plugin-style texts in
ten languages: 25 were refused as descriptions, 17 of them for naming
someone else's verified or official thing ("Opens the official Rust
documentation", "Shows GitHub's verified badge") and 6 for "unofficial" in
languages where it is two words. A rule that refuses honest text that often
is wrong. This section replaces the bare-word refusal **in a summary or
description**. Names and keywords stay as they are: there any mark word is
refused (with the ambiguity narrowing above), because a rename is cheap and
the name sits beside the seal.

- **In a summary or description, a mark word (any listed language, read
  with the same fold, digits and look-alikes) is refused only when it is
  said of the plugin itself:**
  1. it is the text's first word, or stands alone as a sentence
     ("Official Git tools", "Verified.");
  2. it is within two words of a word for the plugin, in either order, with
     no sentence punctuation between ("verified plugin", "official Git
     extension", "cliente oficial", "公式 Git 拡張", "공식 Git 플러그인"):
     a short per-language list in the data file (plugin, extension, add-on,
     integration, client, app, tool, theme, package, version, release,
     build, and their equivalents). Here the ambiguous words count too
     (已认证插件, 認証済みプラグイン), since the neighbour settles the
     meaning, and 公式 needs no kana;
  3. it directly follows a word that says it of the subject ("is", "are",
     "now", "been", "fully", "officially", and equivalents): "is verified",
     "now official";
  4. it is beside "zeron", "the store" or "the plugin store" (the claims
     rule's reach, kept);
  5. the glyphs, anywhere, as now.
- **A negation directly before lifts 1 to 3** (not, no, non, não, nicht,
  не, 非, 비): "not official", "cliente no oficial", "非官方客户端" pass, as
  "unofficial" always did. It does not lift 4 or 5.
- **A standing word after "zeron's" must not catch ordinary prose:**
  "adds a button to Zeron's built-in terminal" passes. "made" and "built"
  count only directly after a bare "zeron" ("Zeron-made", "Zeron built"),
  never after the possessive and never as "built-in" / "built in".
- **The measure:** on the identity lane's corpus, no honest description is
  refused, and every dodge that says the mark of the plugin itself is. A
  text that passes may still be untrue ("the official Linear integration"
  from someone who is not Linear): that is for a reviewer and a report, not
  for this rule, and the page still says "Not verified yet".
- **Refinements from the identity lane's reading, before the build:**
  - A mark word directly followed by a word that gives it an object
    (against, on, with, for, in, from, under, and equivalents) is describing
    a test or someone else's thing: it does not count under 1 to 3
    ("Verified against Node 22", "is verified on macOS 15"). "by" lifts too,
    unless what follows is the publisher speaking of itself or an authority
    (us, our, the team, staff, experts, reviewers, and equivalents).
  - Under 2, a proper noun between the mark word and the word for the
    plugin lifts it ("the official Slack app", "公式 Slack アプリ").
  - 3 also reads lists and contractions ("safe, fast and verified", "It's
    verified", "C'est officiel") and words of degree (completely, totally,
    truly, 100%).
  - The words for a plugin include what plugins are called (editor,
    previewer, viewer, formatter, linter, bridge, connector, helper,
    wrapper, bot, widget, panel, and equivalents).
  - The first word is read after any leading emoji or punctuation.
- **This rule is a filter, not the judge.** It cannot know a sentence's
  subject, and it will not be made to try harder than this. The lists are
  the engine and identity lanes' to settle between them; the coordinator
  rules only where they disagree. The measure on the identity lane's corpus
  (166 honest, 105 dodges): at most 3 honest texts refused and at most 10
  self-claims passing, each one listed with its reason. A reviewer reads
  every version, and a false claim in a summary is a reason not to verify.
  The refusal's sentence names the word and says how to reword.

## Wing's rulings, Nov 18

- **"Zeron" in a name is nobody's concern.** The owner does not want it
  policed at all. `claims_zeron` goes, whole: the name rule and its allowed
  forms, the words of origin, standing and belonging, the summary phrases,
  the keyword part ("zeron" in a keyword is allowed), the device's warning,
  the publish refusal, the transfer refusal, and the suspension on revoking
  `maintainer` (a revoke only revokes). Every section above that describes
  it is void. What says a plugin is Zeron's is the `maintainer` badge, which
  only staff grant; that stays.
- **Unchanged:** the mark rule (the words "verified" and "official" and
  their look-alikes and other-language forms; strict in names and keywords,
  only when said of the plugin in a summary; the glyphs; unseen characters),
  the reserved ids (`zeron*`), and the reserved usernames with their folds.
- **The site's look is approved** (the prototype and the pages built from
  it on `plugin-store/web-look`).
- **A key for many plugins** (the site's Deploy keys, and the same idea in
  the app's words): up to three plugins are named; beyond that the row says
  how many ("14 plugins"), shows three tiles and "+11", and opens the whole
  list in place on request. Nothing is cut off with an ellipsis.
- **The old "Unverified" badge is renamed "Unknown author"** (Wing, Nov 18).
  That badge is the app's existing mark for a plugin whose signer cannot be

- **The staff pages carry no extra figures** (Wing, Nov 18): no "oldest

## The mark rule, frozen (Nov 18)

- **Rule 4 stays whole.** Taking out `claims_zeron` must not take out the
  part of the mark rule that reads the store's own seal: in a summary or
  description a mark word directly beside "zeron", "the store" or "the
  plugin store", in either order, with a space or a hyphen, is a claim of
  the mark ("Zeron verified.", "Zeron-verified.", "Officially
  Zeron-verified.", "Zeron official.", "Store verified."). This is not the
  name policing the owner dropped: "Zeron Git" and "Git by Zeron" pass; a
  name is still refused any mark word at all.
- **What the filter does, measured by the identity lane** on engine
  a490c5a1b and the edge on its files, one answer on both sides (0
  differences over 30,808 strings):
  - its corpus, ten languages: 0 of 166 honest texts refused; 2 of 105
    self-claims passing;
  - a held-out set the lists were then drawn from: 1 of 51 refused; 5 of 38
    passing;
  - a fresh held-out set, written after and never shown to the rule's
    author: 3 of 52 honest refused (CI and changelog language, because
    "build" and "release" are words for a plugin: "verified builds are
    marked green"); 10 of 37 self-claims passing (plugin nouns outside the
    list such as sidebar, edition, controls; CJK claims a few characters
    from the noun; "Simply verified.").
- **Frozen there.** It stops a self-claim that leads the text, sits right
  by a word for the plugin, or follows an "is / now / been" word, and lets
  someone else's verified or official thing through. It does not catch
  every phrasing and will not be widened to try: a reviewer reads every
  version, a false claim in a summary is a reason not to verify, and the
  page says "Not verified yet" until then. The lists change only when a
  real plugin is wrongly refused.
