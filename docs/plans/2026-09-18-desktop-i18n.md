# Desktop i18n: English and Simplified Chinese

> Status: the i18n core, the settings field, the switch path, and phases 1–8 of
> the copy migration are implemented (`crates/ui/src/i18n.rs`, the whole
> Appearance page, the shell and sidebar, the Archived page, the composer and
> pickers, the transcript, diff, history, terminal, files, and markdown
> surfaces, every settings page except the Language entry inside Appearance, the
> UI-authored errors of phases 7, and the Browser pane). Phase 9 moved the copy
> `crates/proto` renders, phase 10 closed the leftovers the earlier phases never
> reached plus the gaps a repository-wide literal sweep turned up, and phase 11
> named the failures `crates/theme` writes itself. Phase 12 flipped the shipped
> default to `System`, which ends the migration. See "Migration status" for what
> is translated and what deliberately stays English.

## Summary

Add a localization layer inside `zeron-ui`, first supporting English and
Simplified Chinese (`zh-CN`). The UI follows the system language by default and
lets the user pin a language in Appearance, switching immediately. English is
the complete fallback and the default for every system that is not Simplified
Chinese; CLI output, logs, panic text, and iOS are out of scope.

Keys are stable semantic ids, translations are compiled into the Rust binary,
and the resolved locale lives in a gpui global. This avoids PR #186's approach
of using English display text as keys (copy edits would break the mapping) and
introduces no runtime resource files or per-render lookups.

## Locale, resources, and runtime state

`crates/ui/src/i18n.rs` holds the core:

- `LanguagePreference`: `System`, `English`, `SimplifiedChinese`. Persisted as
  `"system"`, `"english"`, `"simplifiedChinese"`.
- `Locale`: `En`, `ZhCn` — the resolved value used at render time.
- `MessageId`: stable semantic keys (`AppMenuSettings`, `ComposerPlaceholder`,
  `AppearanceTitle`, `DiffNoChanges`, `AttachmentUnsupportedImage`, ...). Keys
  are append-only for the lifetime of the product; renaming one is a breaking
  change that forces a retranslation.

One declaration table feeds a macro that generates the enum, `MessageId::ALL`,
and an exhaustive `match` for `translate`:

```rust
macro_rules! messages {
    ($( $id:ident = { en: $en:literal, zh: $zh:literal } ),* $(,)?) => {
        #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
        pub enum MessageId { $( $id ),* }

        impl MessageId {
            pub const ALL: &'static [MessageId] = &[ $( MessageId::$id ),* ];
            pub fn english(self) -> &'static str {
                match self { $( MessageId::$id => $en ),* }
            }
            /// `None` while a message is still untranslated (migration only):
            /// an untranslated row declares `zh: ""`.
            pub fn chinese(self) -> Option<&'static str> {
                match self { $( MessageId::$id => (!$zh.is_empty()).then_some($zh) ),* }
            }
        }
    };
}
```

- A missing English string or a duplicate key is a compile error, not a test
  failure. Untranslated messages set `zh` to `""` and are tracked by the
  allowlist in "Migration order and coverage gate" rather than by convention.
- `translate(MessageId, Locale) -> &'static str` allocates nothing; `&'static str`
  enters `SharedString` as the static variant, and `Menu` / `MenuItem` names take
  `impl Into<SharedString>`.
- Dynamic copy gets a macro-generated function per message with typed arguments
  (no generic argument map, no lookup during render), for example
  `relative_minutes_ago(n: u32, locale: Locale) -> String` and
  `attachment_unsupported(kind: &str, locale: Locale) -> String`. Variable
  content (file names, paths, model names, user input) is never translated or
  rewritten.

Runtime state is a gpui global, not a process-wide atomic:

```rust
pub struct I18nState { preference: LanguagePreference, resolved: Locale }
impl gpui::Global for I18nState {}

/// The only place that reads the system locale. Called once at boot.
pub fn init(preference: LanguagePreference, cx: &mut App);

/// Returns `Locale::En` when uninitialized, so host language never leaks
/// into tests or tool paths.
pub fn locale(cx: &App) -> Locale;
pub fn preference(cx: &App) -> LanguagePreference;
```

One process owns one `App`, so a global matches atomic semantics in production,
while gpui's `TestAppContext` builds a fresh `App` per test — locale is isolated
per test and the suite does not need `--test-threads=1`.

## Settings persistence and system language detection

`UiSettings` gains a device-local field:

```rust
pub language: LanguagePreference
```

- `LanguagePreference` implements `Deserialize` with unknown values mapping to
  `System`, following `typography::UiFontFamily`. This is required, not
  defensive: `UiSettings::load` deserializes the whole file with
  `serde_json::from_value::<UiSettings>` and falls back to `Self::default()` on
  any field error, so one unrecognized `"language"` value would reset themes,
  keymap, and pane widths. `serde(default)` covers only a missing field.
- Existing persistence behavior is unchanged: atomic write (temp file +
  rename), corrupt-file fallback, and the current migration steps.
- System language resolves through a pure function so it is testable:

```rust
fn resolve(preference: LanguagePreference, system_locale: Option<&str>) -> Locale
```

| Input | Result |
| --- | --- |
| `English` / `SimplifiedChinese` | The pinned locale |
| `zh`, `zh-CN`, `zh-Hans`, `zh-SG` | `ZhCn` |
| `zh-Hant`, `zh-TW`, `zh-HK`, `zh-MO` | `En` |
| Anything else, or unavailable | `En` |

Traditional-script regions fall back to English instead of being downgraded to
Simplified Chinese; with no Traditional resources, showing Simplified to those
users is the wrong result. The decision lives in this one function, so adding
`ZhTw` later is a local change.

- Read the system locale with `sys-locale`, declared as
  `[workspace.dependencies] sys-locale = "0.3"` and used from `crates/ui`. It is
  already in the dependency graph as `cosmic-text`'s transitive dependency
  (0.3.2 in `Cargo.lock`), so this adds no new third-party code, but Rust
  requires the direct declaration. The read stays inside the i18n module; no
  platform checks scattered through call sites.
- Language affects UI copy only: not the agent, documents, workspaces, the sync
  protocol, user input, fonts, or themes.

## Startup order and runtime switching

Order inside `app.run` in `crates/ui/src/lib.rs`:

1. Load and install `UiSettings`.
2. `i18n::init(ui_settings.language, cx)` — resolve and store the global.
3. Typography, theme, appearance, and the other UI services.
4. Open the main window.
5. `cx.set_menus(app_menus(i18n::locale(cx)))` — still after the window opens,
   because `set_menus` snapshots the keymap for the `⌘`-key equivalents.

Switching goes through one entry point:

```rust
pub fn set_preference(preference: LanguagePreference, cx: &mut App) {
    // 1. resolve and store, returning early when unchanged
    // 2. settings::update(SavePolicy::Immediate, cx, |s| s.language = preference)
    // 3. cx.set_menus(app_menus(locale(cx)))   // same step as boot
    // 4. cx.refresh_windows()
}
```

`refresh_windows()` is the load-bearing call: copy is read during `render()`, and
`notify()` repaints only the entity it notifies. Settings pages are cached
entities (`appearance_page: Option<Entity<AppearancePage>>`) and the composer,
transcript, and pickers are entities too, so notifying "the shell and the current
settings page" leaves stale English behind. `App::refresh_windows()` marks every
window `refreshing`, which makes each view re-run `render()` — the mechanism
`appearance::apply` already relies on.

Switching does not restart the engine, rebuild the window, or change the theme
or data profile.

## Appearance entry point

Add a Language block to `crates/ui/src/settings/appearance.rs`, reusing the
page's existing segmented-selection row and the `widgets::section_card` /
`card_row` scaffolding:

- Title: Language.
- Options: System, English, 简体中文.
- Show the resolved result, for example `System (English)` or `System (简体中文)`.
- Selection calls `i18n::set_preference`, switching all gpui copy and the native
  menu immediately.
- Option labels come from the translation resources like everything else; this is
  not a special English-only surface.
- Independent of theme, light/dark, accent, and surface.

Rules:

- Migrate user-visible display text, tooltips, aria labels, empty states, and
220→  error hints only.
- Keep logs, tracing, debug output, panics, protocol fields, raw agent output,
  repository content, and CLI command names (`zeron update`) in English.
- Never translate product, agent, and model names, paths, branch names, code, or
  user input.
- Enum-provided English labels (`AppearanceMode::label()`, font family labels)
  move to `MessageId`; there is no second source of copy.
- Anything with variables, counts, file names, times, or states goes through a
  structured formatter.
- Relative time gets its own entry point, `relative_time(when, now, Locale) ->
  SharedString`, covering the existing `just now` / `Nm ago` / `Nh ago` /
  `Nd ago` forms. English plural handling lives in the English function; Chinese
  has no plural. The English assertions in `settings/devices.rs` switch to
  passing `Locale::En` explicitly.
- Theme diagnostics: `ValidationIssue.message` and the theme report's
  fallbacks/warnings/dropped/reason strings come from `zeron-theme`. Phase 1
  keeps those payloads in English and translates only the UI-authored prefixes
  (`Adjusted · `, `Warning · `, `Unsupported · `), plus the report's two enum
  labels (`Structural`/`Contrast`, `Warning`/`Error`), which phase 9 moved out
  of a `format!("{:?}")`. This is a recorded limitation
  in "Known limitations", not an oversight.
- Copy that `crates/proto` also renders (the tool chip, the tool-group summary,
  the compact age) keeps its *classification* in proto — one implementation of
  "which tool is this" and "which bucket is this" for every client — and moves
  only the *copy* into this crate's table. Proto keeps its English renderers, so
  no client signature changes and no English is deleted; the duplication that
  creates is converted into an invariant: a test asserts proto's English output
  equals this crate's `Locale::En` output for every chip kind, every summary
  segment and every age bucket. Nothing proto-derived may enter a locale-bearing
  value: `transcript.rs::tool_fingerprint` hashes the chip *kind* and proto's own
  English detail length so a language switch cannot re-splice a tool row.
- Coverage gate: `i18n.rs` holds

```rust
const UNTRANSLATED: &[MessageId] = &[...]; // shrinks with each phase
```

  and a test asserts that the set of `MessageId::ALL` with `zh() == None` equals
  it. The allowlist tracks *registered* messages only, so it says nothing about
  copy that is still an inline literal; the default language therefore flipped
  to `System` (phase 12) once the copy phases were done, not when the list was
  empty. Each phase is verifiable, and a message added without a translation
  fails immediately.
- No business function reads the system locale directly; all copy goes through
  the i18n API.

## Known limitations

- Theme *diagnostics* and raw engine/RPC error strings stay English; Chinese UI
  mixes languages in those places. The library's own named failures (limits, an
  unknown id, a rejected selection, a failed validation) are rows since phase 11;
  what stays English is the importer's file-level messages and the payloads that
  are persisted in the theme library.
- Copy that a page stores before rendering (an inline error strip, a failed
  sign-in message) is resolved when it is stored, so switching language while
  that strip is visible keeps the old wording until the page reloads. Redesigning
  those fields into locale-free types is a larger change than the copy migration
  warranted; `changes::WatchError` and `files::MediaFailure` show the shape it
  would take.
- `accounts::format_reset` keeps `chrono`'s `%a` / `%b` output, so a Chinese UI
  shows English weekday and month abbreviations beside a translated prefix.
- CLI output, logs, tracing, panics, and iOS stay unlocalized.
- The `cfg`-gated platform modules are invisible to a Windows build:
  `appshots/macos.rs` and `appshots/linux/{mod,portal,x11}.rs` are not compiled
  by `cargo check` on Windows, so phase 7's changes there are covered by
  `rustfmt` (a parse-level check), by reading every call site's types, and by a
  byte-level English comparison against `HEAD` — not by the compiler. Changing a
  shared type's shape (`CaptureError::CaptureFailed`) silently breaks those
  modules, so run `cargo check -p zeron-ui --all-targets` on macOS and on Linux
  before shipping. The Browser pane's platform hosts (`browser/macos.rs`,
  `browser/linux/mod.rs`) are in the same position and changed more shape than
  phase 7 did (`NativePage::new`/`load` now return `PageFailure`, and
  `PageState::error` became `Option<PageFailure>`), so the same macOS/Linux
  check is required; an independent read-only audit of both files found no
  mismatch, and it flagged the untestable points (the `define_class!` ivars
  bound, and the `navigate` branch's borrow of `self.native`).
- `browser/linux/helper.c` is compiled only for a Linux target, by
  `crates/ui/build.rs` (`pkg-config webkit2gtk-4.1 json-glib-1.0` plus
  `cc -std=c11`). This machine has neither, so a C edit there cannot be built or
  run: the context-menu labels were therefore localized on the Rust side, and
  the `terminated()` sentence was left alone rather than re-keying it through an
  unverifiable protocol change (a new field in the helper's `state()` JSON).
- Traditional-script regions resolve to English, not Simplified Chinese.
- No runtime resource directory and no external translation format; only the
  `MessageId` + `Locale` structure is extensible.

## Verification

Unit and gpui tests:

- `LanguagePreference` JSON round-trip; a missing field resolves to
  `LanguagePreference::default()` (`System`, see Assumptions); an unknown or
  `null` value resolves to `System` **without disturbing other fields in the
  same file**. The shipped default is asserted directly, together with the three
  `resolve` outcomes it feeds (`zh-CN` → `ZhCn`, `en-US` and `None` → `En`).
- `resolve`: `zh-CN` / `zh-Hans` to `ZhCn`; `zh-TW` / `zh-Hant` to `En`;
  `en-US`, unknown, and `None` to `En`.
- `MessageId` exhaustiveness is enforced by the generated `match`; the
  `UNTRANSLATED` allowlist matches the actual untranslated set.
- Missing Chinese falls back to English — never an empty string, a key name, or
  a raw placeholder.
- Dynamic messages substitute variables correctly and never translate variable
  content.
- `locale(cx) == Locale::En` when i18n is uninitialized, so the host system
  language cannot affect tests.
- `app_menus(Locale::En)` asserts the existing English labels and
  `app_menus(Locale::ZhCn)` asserts the Chinese ones, replacing the current
  five English-only menu assertions.
- Relative time in both locales.
- The copy `crates/proto` also renders agrees with this table: for every chip
  kind and detail shape `tool_chip_content(call) == tool_chip_text(call,
  Locale::En)`, for a tool set covering all nine summary segments
  `zeron_proto::view::tool_group_summary(pairs) == tool_group_summary(tools,
  Locale::En)`, and for every age bucket `format_time_ago(then, now) ==
  time_ago_compact(then, now, Locale::En)`; each has a Chinese expectation beside
  it.
- Switching: after `set_preference` the locale updates and shell, composer, diff,
  and settings copy renders in Chinese (tests set the locale explicitly rather
  than inheriting the host language).
- At least one Chinese-path test each for shell, composer, settings, and diff.

## Assumptions

- Phase 1 covers desktop `zeron-ui` only. `apps/ios` is a hand-written Swift port,
  is not a cargo workspace member, and does not reference `zeron-ui`.
- Only English and `zh-CN` ship now; the `MessageId` + `Locale` structure allows
  Japanese and Traditional Chinese later.
- Translations are compiled into the binary; no runtime resource directory.
- The language preference is device-local in `ui-settings.json` — not in the Loro
  document, the account profile, or multi-device sync.
- PR #186 is not merged directly; only its product behavior (system language,
  settings override, native menu rebuild) is adopted, reimplemented against
  stable semantic keys and the current branch structure.
- Default language, decided at the end: `System`. Every phase of the copy
  migration lands in one change, so the "all phases in the same release"
  condition is met, and what is still English is diagnostics — the theme
  importer's file messages, raw engine/RPC payloads, one WebKitGTK sentence, the
  persisted theme-library warnings — not a half-translated interface. Had the
  migration shipped across releases, the default would have stayed `English`
  until the last copy phase landed; the `UNTRANSLATED` list alone is not the
  gate, since it only covers registered messages.
